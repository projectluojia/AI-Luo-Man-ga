# V3 校巴场景设计

> 状态：首版实施基线
>
> 本文固定首个场景的产品边界和架构边界。具体数据库、智慧珞珈同步协议、前端形态和模型供应商不在本文绑定。

## 一、目标

V3 首个场景归属“校园综合服务 App”。校巴是该 App 中落地的第一组 Capability，用于验证从 Go 内核到 Agent、Service、Tool 和统一存储的完整受治理调用链。

首期业务范围包括：

- 线路和方向查询；
- 站点查询；
- 班次查询；
- 根据出发站、目的站和时间生成出行方案。

实时车辆位置、到站预测和主动提醒只有在权威数据具备相应字段后才开放，不根据静态数据伪造。

## 二、已确定边界

```text
智慧珞珈（唯一权威业务来源）
        │
        │ 官方授权的数据接入，方式可替换
        ▼
Go 托管的统一存储
        │ 仅通过 Storage Port / ctx.storage 访问
        ▼
campus.bus.* Tool（校巴原子包）
        │
        ▼
campus Service（校园业务编排）
        │ 对外仅暴露 Capability
        ▼
Go Kernel → Agent / 前端
```

约束如下：

1. 智慧珞珈是校巴业务数据的唯一权威来源，但同步方式不进入校巴领域逻辑。
2. 数据接入完成后写入 Go 托管的统一存储；Service 和 Tool 不持有数据库凭据。
3. 校巴 Tool 是原子查询或计算包，由 `campus` Service 声明依赖并通过统一 Registry 注册。
4. 校园综合服务使用固定 App 标识 `campus-services`；第一阶段不依赖用户态数据。
5. 没有用户态不等于没有调用上下文。每次调用仍必须携带 `app_id`、`echo_id`、`request_id`、deadline、调用深度和链路信息。
6. 只实现当前团队负责的主运行方案；其他人员负责的对比运行方案共享相同 ToolSpec 和 CapabilitySpec，不复制业务逻辑。
7. 场景范围可以逐步扩展，但公共契约、安全边界、可观测性和测试从第一版按可长期演进标准实现。

## 三、领域归属

| 对象 | 标识 | 职责 |
|---|---|---|
| App | `campus-services` | 校园综合服务的数据、配置和能力空间 |
| Service | `campus` | 校园业务策略及 Capability 门面 |
| Capability | `campus.bus.journeys.search` | 按站点和时间查询可用直达行程 |
| Tool 包 | `campus.bus` | 校巴原子包；注册站点、线路和班次查询入口 |
| Storage namespace | `campus/bus` | 校巴线路、站点、班次和数据版本 |

后续增加线路、站点、换乘规划等能力时，继续使用 `campus.bus.*` 稳定命名空间。模型只能看见 Capability，不直接看见底层 Tool。

## 四、数据约定

校巴领域至少包含：

- `route`：线路、方向及运营状态；
- `stop`：稳定站点标识、名称及位置；
- `trip`：某次班次的始发、终到、发到时间和服务状态；
- `source_revision`：来源版本、同步时间和数据有效期。

内部关联使用稳定 ID，不以可能变化的中文名称作为主键。所有时间带明确时区；原始来源记录保留版本和更新时间，以支持审计与回滚。

数据库实现必须满足 Storage Port。无论后续采用定时同步、事件推送、接口拉取或校方数据平台，校巴 Service 与 Tool 的公开契约保持不变。

## 五、首条验收链路

1. Go 创建包含 `app_id` 和 `echo_id` 的请求上下文。
2. Router 确认 App 已启用 `campus.bus.journeys.search`。
3. Registry 将 Capability 路由到 `campus` Service。
4. Service 通过统一 Dispatcher 使用 `campus.bus.journeys.search` Tool。
5. Capability 输入先按 Registry 中已编译的严格 JSON Schema 校验，Service 调用 Tool 时由 Go 再次校验并收窄权限。
6. Tool 通过注入的 Storage Port 查询数据，不接触数据库连接信息。
7. 结果沿原调用链返回，错误保持结构化且可追踪。

验收至少覆盖：注册原子性、严格 Schema、未启用能力拦截、权限不放大、App 隔离、请求校验、空结果、时间过滤、结果排序、调用深度限制和并发安全。当前校巴查询均声明为 `read`，不产生业务副作用。

## 六、暂不绑定的实现

- 智慧珞珈的数据同步协议；
- 统一数据库的具体产品和物理表结构；
- 校方统一身份接入方式；
- Agent 模型与前端交互形态；
- 其他人员负责的额外 Tool 运行方案。

这些内容通过适配器接入，不得反向改变本文定义的领域和治理边界。

## 七、AI Agent 与 Web Access

Python Agent 必须由真实模型驱动。Go 将本 Run 有权使用的 Capability 描述和 JSON Schema 下发给 Agent；模型适配器将其转换成厂商原生 tools。模型原生 ToolCall 被还原为 CapabilityCall，经 Go 鉴权、路由和审计后执行，再把结果交回模型继续推理。

生产运行路径禁止用关键词、正则或固定业务流程替代模型选择。测试可注入可控 ModelProvider，但没有模型配置时生产 Agent 必须拒绝就绪。

当前 Go/Python 协议要求版本握手、双向独立严格序号、帧与字段大小限制、未知字段拒绝、重复 ToolCall 拒绝和终态后迟到帧拒绝。多个模型 ToolCall 按 Provider 索引顺序串行执行。每步模型调用必须上报 Token 用量并受持久化 Run 预算约束；Provider 只在尚未收到流数据时对可重试故障执行有界退避，取消和超时直接传播。校巴 Tool 仍只接收经过 Go 再校验和授权的 CapabilityCall。

校巴包不定义递归或子任务语义。Executor 若需要递归，由自身在受治理的 executor.v1 会话中调用自身；Core 只按当前 Run 的取消、deadline、Capability 投影和预算处理请求，不提供某个 Executor 专用的创建/查询子任务 API。

校巴查询只使用 SQLite 中由 `bus_current_snapshots` 指向的单一完整修订。快照必须显式声明完整性、权威性、导入时间和有效截止时间，并在原子激活前通过 ID、重复、引用和时间一致性校验。成功结果携带 `data_status=authoritative_fresh` 及修订/有效期；缺失、不完整、非权威或过期修订返回稳定治理错误且不返回业务行。演示快照始终非权威，在生产环境禁止加载，在开发环境也不能被 Agent 当成当前事实。

首个外部接入为 Go Web Access：创建 Echo、查询状态、订阅 SSE 流、取消运行和查看可见 Capability。仓库只提供极简联调页面，不承担产品前端设计。
