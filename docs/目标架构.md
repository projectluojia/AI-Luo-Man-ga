# AI珞 目标架构（统一模型）

> 状态：**设计**。本文是目标形态的唯一权威表述，整合 `v3_overall_design.md`、
> `包管理器设计.md`、`重构后架构设计.md` 中关于目标架构的分散描述。
> 每一节标注实现状态：【已实现】= 代码与测试已落在 `refactor/target-architecture`
> 分支；【目标】= 设计已定、待实施（见 §9 路线）。

## 一、设计公理

**内核不含任何功能，也不含智能。** 功能与智能全部在包里：bus 是包，agent 也是包，
school-auth（学校系统鉴权）还是包。内核只做四件事：**装载包、编排任务图、
治理调用、持有状态**。

推论：
- 内核只认**角色**，不认**名字**。内核代码里出现任何具体运行时的名字
  （如 `ailuo.agent`、`python`、学校系统地址），即视为架构违例。
- Core 与包的关系是**组合关系**：本 App 的 executor 由哪个包充当、启用了哪些
  Capability，全部是 **App 配置数据**，不是代码。
- 发行版 = 内核 + 一组随发的包。我们这样发，别的团队也这样用——装同一套包进
  他们自己的内核，或实现公共运行时契约后直接嵌入（§8）。

## 二、四层模型

```text
分发脊柱（package manager，唯一入口）
  包 = 版本化发布物，按组件形态分两种（见 §4）
  包源：远程仓库（GitHub Release）/ 本地目录
  入口唯一：ailuo install → 安装目录 → 发现 → 校验 → 注册

运行层（Loader，唯一执行模型）
  Runtime = 清单化执行单元
  {id, version, mode, role, digest, storage, 宿主函数声明, 进程规格}
  生命周期统一：register → load → ready → drain → stop

调用层（Dispatcher + 任务图）
  一切功能 = Capability，全部过 Dispatcher：权限投影、幂等、确认、审计
  任务图管理包间调用：agent 调服务、服务调 agent、定时管线……
  两条产品管线共用它：Agent Run（长会话）/ 直接 RPC（HTTP/SDK）

状态层（存储端口，唯一权威）
  SQLite 统一数据库；一切运行时无状态；卸载/升级不丢数据
  内核是唯一存储写者：任何包（含持凭据的）都不直接落库
```

### 核心概念四件套

| 概念 | 定义 | 生命周期 |
|---|---|---|
| **Package** | 分发/版本/升级单位，含 N 个组件 | 安装、升级、卸载、发布 |
| **Runtime（组件）** | 执行单元，一种 mode + 一种 role | 注册→装载→就绪→排空→停止 |
| **Capability** | 调用面，功能的最小可见单元 | App 显式授权后可调用 |
| **App** | 业务/数据/授权边界（每个团队一个 App） | 授权能力、选择 executor |

## 三、角色与信任模型

**role 与 mode 是正交的两轴**：role 答"做什么"（capability 被调用 / executor 发起
调用），mode 答"在哪跑"（hosted 关在内核进程内的 wasm 沙箱 / isolated 独立进程
走协议通信）。

| | role=capability | role=executor |
|---|---|---|
| **mode=hosted**（wasm 沙箱） | bus、agent 包的 `prefs` 组件——无状态、被动、只被调 | ✗ 不可能存在：沙箱无出站，装不下思考者 |
| **mode=isolated**（独立进程） | school-auth——签名信任，可出站取数 | agent 的 `brain` 组件——签名信任，持凭据调 LLM |

- **被动性跟形态走，功能性跟角色走**：hosted wasm 天然无状态（自身状态经
  `ailuo.store` 落内核）且被动（不能发起调用）；isolated 进程可出站——所以凡
  isolated 一律签名。
- 信任等级与凭据：

| 形态 | 信任等级 | 凭据 |
|---|---|---|
| hosted wasm（capability） | 不可信沙箱 | 永不持有 |
| isolated 进程（capability / executor） | 低信任 → **签名显式信任** | 由该包的 Deployment/监督器准备，通用 Host 只执行最终 ProcessSpec |
| 内核 Go 代码 | 可信计算基 | 全部 |

信任判据：**capability 包回答"系统能做什么"，executor 包回答"谁来思考"，
内核代码回答"规则是什么"。三者不互换。**

## 四、分发脊柱【capability 部分已实现；executor/签名为目标】

- `ailuo install / upgrade / uninstall / list / pack / publish` 是组件进系统的唯一入口。
- 不存在"内置包"分支：所有包都经 manifest、lock、PackageSource 和 Loader
  接入；Core 只按角色发现运行时，不按包名写启动逻辑。【目标，见 §9 阶段 2a】
- capability 包：wasm 组件（hosted）或进程组件（isolated），导出 Capability，
  数据经 `ailuo.store` 宿主函数读写宿主存储，**新增有状态包零内核改动**。【已实现】
- executor 包：进程组件，声明进程模板与资源限额；实际 Provider 配置由包的
  Deployment 管理，不进入通用 Core Host；必须过签名信任链。【目标，见 §9 阶段 2b】
- **签名规则**：任何需要网络出站或凭据的包（agent、school-auth）都必须签名；
  纯沙箱 capability 包保持 SHA-256 锁定即可。

## 五、运行层【部分已实现】

- **单一运行时身份**：`Manifest {id, version, mode, role, digest, storage, host_functions}`
  覆盖一切执行单元。digest 必须对应真实工件，禁止对常量字符串求哈希。【已实现；
  executor 与 capability 均来自安装目录记录】
- **宿主函数 = 内核特权能力的唯一暴露语法**：声明式（`ailuo.store` 即范式），
  声明 ⊆ 授权在装载期 fail-closed 校验。禁止为任何包手写定制投影。【已实现】
- **进程组件声明制**：进程模板和资源限额来自包清单，安装器生成锁定的绝对
  ProcessSpec，通用进程宿主只校验并执行它。【已实现目录工件与模板；签名仍是阻塞项】
- **按角色解析**：内核/App 需要 executor 时按 Role 解析租约，不存在专属接口。
  【目标，见 §9 阶段 2a】

## 六、调用层与任务图

- **一切功能 = Capability，全部过 Dispatcher**（权限投影、幂等、确认、审计、取消）。
  Agent 的 ToolCall 与外部 HTTP/SDK invoke 是同一扇门的两条走廊。【已实现】
- **任务图系统**【底座已实现，泛化为目标】：现在的 Echo→Run 树（`parent_run_id`、
  持久队列、租约、崩溃恢复、子图）就是任务图的骨架——节点 = Run，边 = 调用。
  泛化方向：节点类型从"只有 agent 会话"扩展为**任意包调用节点**
  （agent 会话节点、capability 节点、定时节点），调度、预算、取消、恢复语义共享。
  照旧不预先造通用 DAG DSL，节点类型按需加。
- **包间组合只发生在两处**，沙箱 guest 直调其他包的能力**永不做**：
  1. 任务图组合（编排期）：内核按图调用各包能力（如学校数据管线）；
  2. agent 会话组合（运行期）：agent 经受治理会话调用任意已授权 Capability
     （今天 agent 调 bus 即此路径）。
  数据流因此保持单向与可审计：`school-auth 取数 → 内核校验落库 → bus 读快照`，
  bus 永远不需要直调 school-auth。
- **第一个真实任务图 = 学校数据管线**（§9 阶段 2c 的驱动）：
  `定时 → school-auth.fetch（学校系统鉴权取数）→ 校验 → 快照原子写入 → 完成事件`。
  全程过 Dispatcher 审计；写入是内核唯一写者语义（`ReplaceSnapshot` 仅可信 Go 侧）。

## 七、状态层【已实现】

- SQLite 统一数据库是唯一权威：Echo/Run/配置/审计/幂等/包文档
  （`package_documents` + 快照元数据）。运行时与包无状态，卸载不丢数据。
- **学校数据只能经鉴权获得，且只落内核存储**：任何包（bus guest、别的团队的
  调用方）读到的都是经过治理的快照数据——含来源、权威性、有效期元数据，
  过期/非权威数据由 guest 侧治理规则显式拒绝。

## 八、agent 的位置【去特殊化为目标】

agent = **一个普通的 executor 包**，与 bus 平级：
- 它需要通用宿主（进程生命周期、资源限额、监督），自己的 Provider 配置由包部署负责；
- Core 与它的关系是安装目录中的 `RoleExecutor` 记录，不在代码中硬编码包 ID；
- **别的团队复用 agent 的两条路径**：
  1. 部署复用：他们运行自己的 AI珞 内核，`ailuo install` 我们的 agent 包；
  2. 嵌入复用：他们实现公共运行时契约（`runtime.v1`，阶段 3 的产物）作为宿主，
     直接运行 agent 包的进程组件——契约是版本化 gRPC，语言无关；
- 验收判据：`internal/app` 不包含 Python 路径、Provider 环境映射、Agent 源码或内置包源。

**agent 包的目标构成（双组件）**【目标，随阶段 4】：
- `brain` 组件（isolated，role=executor）：认知会话 + **上下文装配**——装配是认知
  策略，属于大脑本身：个性化渲染、偏好合并都在此完成；
- `prefs` 组件（hosted wasm，role=capability）：偏好增删改查，经 `ailuo.store`
  读写 agent 自己的 namespace；
- 原内核 `prompt` 服务随之消解：状态 → agent namespace 文档，CRUD → `prefs`
  导出的能力，渲染 → `brain` 内逻辑。内核保留：会话历史存储、帧级预算强制、
  边界脱敏。历史原因说明：prompt 当年放内核的唯一硬理由是它拥有持久化状态，
  `ailuo.store` 落地后该理由消失。

## 九、鉴权与多团队

**两层鉴权，勿混为一谈**：

1. **数据源鉴权（学校系统）**= 独立的 `school-auth` 包：
   - 形态：isolated capability 包，**签名信任**（持智慧珞珈 OAuth 凭据）；
   - 职责：OAuth 令牌管理 + 授权取数，以 Capability（如 `school.fetch_dataset`）暴露；
   - 边界：**只取数、不落库**——内核任务图调用它，校验后由内核原子写入快照；
   - 全系统唯一通道：任何包需要学校数据，要么调 school-auth 的 Capability，
     要么读它取回并经内核校验落库的快照。没有第二条路。
2. **平台鉴权（别的团队用 bus）**= 既有 App 模型，无需新造：
   - 每个团队一个 App：identity/membership/App 级授权已实现；
   - 团队凭据（API 凭据）经 Web/SDK 边界进 Dispatcher，App 级权限投影 + 审计生效；
   - 包数据天然按 App 隔离（`app_id × namespace`），团队之间互不可见。

## 十一、刻意不统一与公理的完整达成

1. **内核治理面（identity、App 配置控制台）不进 Loader**：它们是**规则本身**，
   不是功能——给规则造运行时身份 = 重新发明无消费者的抽象。
2. **Run 与 RPC 两条入口管线保留**：长会话产品与短请求产品，底层共享 Dispatcher；
   合并只会造出四不像。
3. **沙箱 guest 直调其他包的能力，永不做**：包间组合只走任务图与 agent 会话
   （§6），两者都过 Dispatcher 治理。

阶段 4 完成后，"内核不含任何功能"公理**完整成立、零例外**：功能在包里，智能在
executor 包里，内核只剩装载、任务图、治理与状态。
