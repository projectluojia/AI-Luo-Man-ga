# AI珞 V3 重构后目标架构设计

> 状态：目标架构设计，不代表全部实现已经完成。
>
> 日期：2026-08-30
>
> 本文描述包管理器独立、Agent Service 化、Go Core 解耦和持久执行内核重构后的目标形态。当前代码证据以 `docs/系统架构说明.md` 和 `docs/仓库状态与路线图.md` 为准。

## 1. 设计目标

本次重构解决四个问题：

1. Go Core 不依赖任何具体 Service、Agent、数据库或包管理器实现。
2. Agent 与 Campus、Prompt 等 Service 使用同一套 Package、Component、Runtime、权限和升级模型。
3. 包管理器可以迁移到独立仓库，Core 只依赖稳定的包契约和加载端口。
4. Echo/Run、任务队列、Capability 调用和生命周期各自拥有清晰的事实来源与责任边界。

### 1.1 非目标

以下内容不属于目标：

- 默认拆成微服务、多个数据库或多个消息代理。
- 为每个类型、文件或调用点增加接口。
- 引入万能 `Manager`、`Factory`、`Utils` 或通用 Service 基类。
- 用 Kafka 取代 Echo/Run 状态机。
- 用新的兼容转发层长期保留旧模型。
- 把不同边界的 Manifest、Runtime、Capability 类型强行合并。

当前项目优先采用模块化主程序和少量独立 Runtime。逻辑边界先稳定，物理拆分由规模和运维需求决定。

## 2. 基本概念

| 概念 | 责任 | 事实来源 |
| --- | --- | --- |
| Deployment | 一套物理运行环境，包含 Go Core、Runtime、存储和已安装包 | Go 管理的部署配置 |
| App | Deployment 内的数据、权限、会话和 Agent 配置边界 | Go 持久化控制面 |
| Package | 分发、版本和升级单位 | manifest + lock |
| Component | Package 内的运行单位 | component manifest + Runtime |
| Service | 具有业务语义、对外暴露 Capability 的逻辑装配体 | Registry 元数据 |
| Tool | 可复用的原子能力 | Tool Registry 与实现 |
| Runtime | 执行 Component 的实现 | Loader 与运行时状态 |
| Executor | 执行一次 Run 的 Runtime 角色 | `executor.v1` |
| Run | Go 管理的持久执行记录 | Run Store |
| Capability | 经过 Go 治理的对外操作入口 | Registry + Dispatcher |
| CapabilityCall | 一次受治理的调用请求 | Run 事件与审计 |

Package 是分发边界，Service 是逻辑能力边界，Component 是运行边界。三者不互相替代。

### 2.1 Agent 的定位

Agent 是普通 Package 和普通 Service。它与其他 Package 共享以下机制：

- manifest、lock、版本和摘要；
- hosted/isolated Component 模型；
- Loader 发现、验证、升级和停止；
- App Capability 投影和权限收窄；
- 审计、取消、预算和健康检查。

Agent 只声明一个标准运行角色：`RoleExecutor`，并实现版本化的 `executor.v1` 协议。这个角色约束不授予 Agent 绕过 Dispatcher、Storage 或权限边界的能力。

Agent 的 Python 进程是一个 isolated Component。Python 包的 uv 依赖属于 Agent 自己的 Python 模块；Ailuo Package lock 管理部署工件、进程规格和摘要。两种锁分别管理不同边界。

### 2.2 hosted 与 isolated

两种模式都需要运行时：

```text
hosted   → Go 管理的进程内 Host，当前主要是 WASM
isolated → Go 管理的独立进程或独立执行环境
```

一个 Package 可以包含混合 Component：

```text
agent.pkg
├─ agent-executor  isolated  Python executor.v1
└─ agent-helper    hosted    只有在存在真实纯计算能力时才增加
```

没有可执行代码的配置、Schema、权限声明、提示词模板和 SDK 契约属于 manifest/extensions，不增加 `mode: none` 的虚假 Component。

                              ▼

              │                      │
              ▼                      ▼
┌─────────────────────┐  ┌──────────────────────────┐

└─────────────────────┘  └──────────────────────────┘

### 3.1 逻辑平面

```text
治理控制面
├─ Identity / App / Policy
├─ Registry / Dispatcher
├─ Confirmation / Idempotency
└─ Audit / Observe

持久执行面
├─ Echo / Run 状态机
├─ Child Run
├─ Durable Work Queue
├─ Scheduler / Lease
└─ Cancel / Retry / Recovery

能力提供面
├─ Agent Service
├─ Campus Service
├─ Prompt Service
└─ 其他 Package Service / Tool

基础设施面
├─ SQLite 或未来 Go-managed Database
├─ Runtime Host
├─ gRPC / Protobuf
└─ 文件、Blob、外部平台适配器
```

逻辑平面不决定进程数量、端口数量、队列数量或数据库数量。Agent 可以独立进程运行，Campus 可以 hosted WASM 运行，但它们仍然处于同一个能力提供面。

### 3.2 Deployment 与 App

```text
Deployment
├─ Go Core
├─ Shared Registry metadata
├─ Runtime Host / Worker pool
├─ Package install root
├─ Go-managed Storage
├─ Agent Executor Package
├─ Service / Tool Packages
└─ App[]
   ├─ members / roles / permissions
   ├─ agent configuration
   ├─ enabled capabilities
   ├─ sessions / messages / echoes / runs
   └─ app-scoped data namespaces
```

Package 安装在 Deployment 层。App 只决定是否启用以及允许哪些 Capability。代码和 Runtime 可以共享，业务数据、权限和会话必须按 `app_id` 隔离。

## 4. 依赖规则

箭头表示编译期依赖：

```text
cmd/ailuo-core ──> internal/app
internal/app ────> kernel / access / adapters / service assembly
access ──────────> kernel public ports + contracts
services ────────> contracts + approved kernel ports
adapters ────────> kernel ports + contracts
kernel ──────────> contracts + standard library
```

必须禁止：

```text
kernel ──X──> internal/services/*
kernel ──X──> internal/access/*
kernel ──X──> SQLite concrete implementation
kernel ──X──> Python Agent implementation
kernel ──X──> packagefmt / GitHub package client
packagefmt ──X──> internal/kernel/*
pkg/* ──X──> internal/*
Tool ──X──> Service implementation
Agent ──X──> business database or external platform
```

Service 可以实现 Kernel 定义的端口，Adapter 可以实现 Storage、Runtime 和外部协议端口。组合根可以依赖全部实现，但不包含业务规则。

### 4.1 端口放置规则

不建立一个收集所有接口的全局 `ports` 包。接口放在实际使用它的边界附近：

| 使用方 | 端口示例 |
| --- | --- |
| Echo Orchestrator | Run 创建、执行、恢复、事件和取消 Store |
| Scheduler | queued 查询、Run 执行和批量取消 |
| Dispatcher | Capability Handler、Policy、Confirmation |
| Loader | Package Source、Runtime Host、Artifact Reader |
| Access | Echo Admission、Echo Reader、Access Admin |
| Agent Host | `executor.v1` Client 和进程生命周期 |

一个接口只有在消费方需要隔离实现、权限或测试替身时才存在。接口不承担未来猜测。

### 5.1 Core 拥有的规则

| 规则 | 唯一拥有者 |
| --- | --- |
| 外部身份到内部用户的解析 | Access Hub + Identity |
| App 成员和权限上界 | Identity / App Policy |
| Echo 与 Run 原子创建 | Echo Orchestrator + Store transaction |
| 新 Echo 创建后通知 Scheduler | Echo Admission |
| Run 状态和 attempt 转换 | Echo Orchestrator |
| queued Run 领取、租约、取消和恢复 | Run Scheduler |
| Capability Schema、权限和确认 | Dispatcher |
| Tool/Service/Capability 元数据 | Registry |
| Package 到 Runtime 的信任边界复验 | Loader |
| 系统日志、指标、审计和脱敏 | Observe / Audit |
| 主服务停止顺序 | App Lifecycle |

业务 Service 只表达业务规则。Tool 只表达原子能力。Agent 只表达认知循环或 Executor 实现。

### 5.2 Echo Admission

所有入口使用同一条 Core 用例：

```text
Access Hub.Intake
    ↓
EchoAdmission.Create
    ├─ Orchestrator.CreateIdempotent
    └─ 新建成功后 Scheduler.Enqueue
```

`Enqueue` 只负责降低轮询延迟。queued Run 已经持久化，恢复路径直接读取持久队列。Web、QQ 和 Ingress 不再分别实现“创建后入队”逻辑，也不直接持有 Scheduler 依赖。

### 5.3 Core 不直接依赖 Agent

Core 使用通用执行端口：

```text
Run Scheduler
    ↓
ExecutionRuntime / executor.v1
    ↓
任意 RoleExecutor
```

Agent 是第一个实现。未来可以接入 workflow executor、batch executor 或远程 executor，而不修改 Run 状态机和 Dispatcher。

Core 可以定义 child Run 的治理规则，但不定义 Python Agent 的模型循环、Provider 或提示词实现。

## 6. 持久执行与任务队列

### 6.1 Run 执行流程

```text
Create Echo
    ↓ 原子写入 Echo + queued Run
Scheduler notification
    ↓
Claim queued Run + lease
    ↓
ExecutionRuntime.Run
    ↓
Agent/Executor 返回 text、usage 或 CapabilityCall
    ↓
Dispatcher 校验并执行 CapabilityCall
    ↓
把 CapabilityResult 返回 Executor
    ↓
持久化事件、用量和终态
```

Scheduler 的进程内 channel 只负责唤醒 worker。数据库中的 queued Run 才是权威队列。

### 6.2 状态不变量

- Echo 创建和第一条 queued Run 在同一个事务内提交。
- Scheduler 只领取持久化的 queued Run。
- 每次领取都带有界 lease。
- Worker 崩溃后，Go 按启动策略处理遗留 running Run。
- retry attempt 由 Go 根据持久配置创建，Python 不私自重试 Run。
- write/external 副作用后的未知结果不自动重做。
- child Run 由 Go 创建，带 `parent_run_id`、独立预算和收窄后的权限。
- 事件序号、ToolCall、用量和终态都按 App/Run 持久化。

### 6.3 Kafka 的边界

Kafka 是追加日志和事件分发系统，提供分区顺序、消费者位点和保留策略。它不是 Echo/Run 状态机，也不负责：

- 状态转换的业务合法性；
- App 权限隔离；
- Run lease；
- child Run 关系；
- Capability 权限和 Schema；
- HTTP/SSE 取消；
- 外部副作用幂等。

当前规模继续使用 Go Core + SQLite durable queue。未来需要多节点队列时，优先增加 PostgreSQL 等 Go-managed Store Adapter；需要高吞吐事件广播时，再增加 Kafka/NATS 等事件 Adapter。Core 的 Run 状态和治理契约保持不变。

Kafka、NATS 或工作流引擎只能放在 Adapter 后面。引入前必须证明当前 SQLite/Store 不能满足吞吐、节点数或恢复时间要求。

### 6.4 Run Scheduler 与 Task Scheduler

两者都处理持久任务，但语义不同：

| 调度器 | 任务 | 特殊规则 |
| --- | --- | --- |
| Run Scheduler | Echo、root Run、child Run、Executor 调用 | Capability、预算、事件、父子关系 |
| Task Scheduler | 确认过期、后台维护、周期任务 | Task 类型、lease、周期和后台重试 |

两者可以复用事务、lease 和观测基础能力。除非出现稳定的相同状态机，否则不合并为万能 Scheduler。

### 6.5 成熟库使用原则

| 能力 | 选择 |
| --- | --- |
| HTTP、Context、JSON、Hash、文件 | Go 标准库 |
| gRPC、Protobuf | 官方成熟实现 |
| 数据库 | Go-managed 数据库驱动与事务能力 |
| semver | 已锁定的成熟库 |
| Run 状态、权限和 child Run | Core 自己实现 |
| 当前 durable queue | Store Adapter + 显式 Scheduler |
| Kafka/NATS | 只有真实事件分发需求时引入 |
| Temporal 类工作流系统 | 只有接受外部工作流服务和新的事实来源后评估 |

Core 自己拥有领域语义，底层通信、数据库和协议使用成熟实现。

## 7. Agent Package 与 Executor Runtime

### 7.1 Python Agent 仓库

```text
ailuo-agent/
├─ pyproject.toml
├─ uv.lock
├─ agent/
│  ├─ runtime.py
│  ├─ core.py
│  ├─ model.py
│  └─ providers/
└─ tests/
```

Python Agent 实现 `executor.v1`：

- 接收 Go 投影的 Run 输入和 Capability 列表；
- 调用真实模型 Provider；
- 使用 Provider 原生 ToolCall；
- 返回结构化 CapabilityCall；
- 接收 Go 返回的 CapabilityResult；
- 返回文本、用量、错误和终态。

Python Agent 不直接访问数据库、外部平台、Registry 或 Package 安装根目录。

### 7.2 Core 侧只保留通用能力

```text
internal/kernel/executor/
├─ contract.go
├─ client.go
└─ protocol.go

internal/adapters/runtimehost/
├─ process.go
└─ grpc.go
```

`runtimehost` 只处理进程、地址、资源限制、gRPC 连接、退出监督和回收。它不写死 Python 模块、Provider 或模型厂商。

如果部署平台已经启动 Agent，Core 直接连接 `executor.v1`，不需要进程监督 Adapter。

### 7.3 Child Run 能力

当前 child Run 能力本质上是 Core 的 child Run 控制面：创建关系、收窄权限、固化预算、排队、取消和查询状态。

目标契约使用通用名称：

```text
run.create_child
run.get_child_status
```

该能力由 Core 注册和治理。Agent 通过普通 CapabilityCall 请求它，不能在 Python 进程内私建子任务。

名称调整发生在版本化 Capability 契约边界，不保留长期双名称兼容路径。

### 7.4 Agent 的混合 Component

Agent Package 可以包含多个 Component：

```text
agent.pkg
├─ agent-executor
│  └─ isolated / RoleExecutor / executor.v1
└─ agent-helper
   └─ hosted / 真实的纯计算能力
```

只有存在真实可执行能力时才增加第二个 Component。Service metadata、Schema、权限声明和配置不作为无运行时 Component。

## 8. Service、Tool 和 Capability

### 8.1 Service

Service 是业务装配体：

```text
Service
├─ 声明 ToolDependencies
├─ 声明权限上界
├─ 组合 Tool
├─ 暴露 Capability
├─ 声明 storage namespace
└─ 通过 Go 端口使用系统资源
```

Service 不拥有：

- 用户体系；
- 私有数据库凭据；
- 外部平台连接；
- 独立的公共 HTTP/QQ 出口；
- 未经 Go 跟踪的调度器；
- 全量 Tool 目录。

### 8.2 Tool

Tool 表达一个原子副作用边界：

```text
Tool
├─ input/output schema
├─ side_effect
├─ required_permissions
├─ Runtime declaration
└─ 一个可验证的原子处理过程
```

多个 Service 需要相同能力时，抽成 Tool。只有一个 Service 使用的逻辑留在 Service 内，避免提前包化。

### 8.3 CapabilityCall

所有调用统一经过：

```text
Agent / Service
    ↓ CapabilityCall
Go Dispatcher
    ├─ App enabled 检查
    ├─ Scope 收窄检查
    ├─ Schema 校验
    ├─ Confirmation 校验
    ├─ Idempotency 校验
    ├─ Runtime acquire
    ├─ Tool/Service 执行
    └─ Audit / Event
```

Service 间协作使用 Capability，不保存彼此私有地址。Tool 不反向依赖 Service 实现。

## 9. Package Manager 与 packagefmt

### 9.1 包管理器目标仓库

```text
ailuo-packages/
├─ cmd/ailuo-pm/
├─ pkg/packagecontract/
│  ├─ manifest.go
│  ├─ format.go
│  ├─ semver.go
│  └─ jsonio.go
├─ pkg/packmgr/
│  ├─ installer.go
│  ├─ registry.go
│  ├─ pack.go
│  └─ integrity.go
├─ pkg/packagefmt/
│  ├─ source_manifest.go
│  ├─ schemaextract/
│  └─ build.go
├─ pkg/sdkgen/
```

`pkg/packagecontract` 是包格式的唯一公共契约；`pkg/packmgr`、`pkg/packagefmt` 和 `pkg/sdkgen` 分别提供分发、作者和消费工具。它们都不能依赖 Go Core 的 `internal` 包。

### 9.2 packagefmt 迁移要求

目标 `packagefmt` 已移到 `pkg/packagefmt`，生产代码不再依赖 Go Core 的 `internal` 包。剩余仓库迁移需要保持以下边界：

1. Tool/Service/Capability 的 JSON 契约移到版本化公共包。
2. 包格式 ID 和路径规则移到包契约或 packagefmt 自己的公共规则。
3. 依赖 Loader 的 hosted protocol 验证移出 packagefmt。
4. `packagefmt` 只保留 `ailuo.toml`、源码提取、Schema 和构建。
5. `packagecontract` 保留 manifest、lock、版本、路径和进程声明；`packmgr` 只保留安装、升级、发布和完整性。
6. SDK 生成只消费公共 Capability Contract。

当前 `pkg/packagefmt` 已可以在同一模块内作为公共包构建；迁移到独立 package manager module 时只需迁移公共契约和包管理器相关依赖，不得重新引入 Core `internal` 依赖。

### 9.3 Loader 与包管理器

Loader 不依赖 GitHub、tarball 打包或 package manager 的安装实现。Loader 只依赖：

```text
Package Contract
InstalledPackageSource port
Artifact Reader port
Runtime Host port
```

本地 packmgr、远程注册表和未来其他包管理器都通过 `PackageSource` Adapter 接入。

Loader 仍然要在自己的信任边界重新校验 manifest、lock、摘要、路径、进程规格和宿主函数。包管理器的预校验不能替代 Loader 校验。

## 10. Access 与外部入口

### 10.1 入口链路

```text
Web / QQ / Platform Adapter
    ↓
Access authentication and normalization
    ↓
Hub.Intake
    ↓
Identity / Session / Message
    ↓
EchoAdmission.Create
    ↓
Core Scheduler
```

Web、QQ 和 Ingress 不直接写 Echo/Run 表，不直接访问 Loader 或 Registry。

### 10.2 接入排空

每个接入入口拥有自己的 admission gate：

```text
StopAccepting
    ↓
拒绝新接入
    ↓
WaitAdmissions
    ↓
确保 Create + Enqueue 已完成
```

Web、Ingress 和 QQ 的 Gate 相互独立。App Lifecycle 在关闭 Scheduler 前停止所有入口并等待所有 Gate。

### 10.3 Ingress 信任边界

Ingress 的身份、签名、防重放和平台来源绑定属于独立安全能力。接入排空不能替代机器认证。

在认证边界落地并通过测试前，文档必须将 Ingress 认证标记为未完成，不得将当前 HTTP 入口描述为可信平台入口。

## 11. Storage 与数据所有权

### 11.1 数据所有权

```text
Go Core owns:
  user / identity / membership
  app / policy / confirmation
  session / message / echo / run
  event / audit / package install state

Service owns:
  business rules
  declared storage namespace
  business records through Storage API

Python Agent owns:
  current model turn scratch only
```

Python scratch 丢失后，Go 根据持久 Run 策略决定失败、取消或重试。Python 不成为系统事实来源。

### 11.2 Store 端口

Core 根据消费者需要组合端口：

```text
EchoCreationStore
RunExecutionStore
RunRecoveryStore
RunCancellationStore
EchoEventStore
CapabilityAuditStore
PackageSource
```

SQLite 是当前 Adapter。未来替换 PostgreSQL 或其他 Go-managed 数据库时，只替换 Adapter 和迁移实现，不修改 Dispatcher、Run 状态机和 Service 契约。

所有读写在 API 和 SQL 边界验证 `app_id`。所有状态转换在事务内完成，Schema 使用外键、唯一约束、CHECK 和复合索引。

## 12. 协议与安全边界

### 12.1 公共协议

```text
ailuo-contracts/
├─ package.v2
├─ capability.v1
├─ executor.v1
└─ runtime-host.v1
```

协议使用 Protobuf/gRPC 或明确版本化 JSON 契约。公共 HTTP、SSE、manifest、lock、Capability Schema 和持久事件都属于版本化接口。

### 12.2 调用安全

- Go 为每个 Run 计算 Capability 投影。
- Agent 只能请求投影内的 Capability。
- Dispatcher 在 Go 信任边界重新校验 Schema、权限、幂等和确认。
- 内部调用只能收窄权限，不能提权。
- 所有跨进程消息限制大小、字段和序号。
- 非 loopback 边界使用认证传输。
- 公共错误不返回 SQL、路径、堆栈、Provider 响应或秘密。
- 副作用未知结果进入人工或对账路径，不自动猜测结果。

### 12.3 Runtime 安全

```text
Package manifest
    ↓ package validation
Installed lock
    ↓ Loader revalidation
Runtime Host
    ↓ limits / protocol / health
Dispatcher acquire
    ↓ per-call governance
Runtime Invoke
```

Package 声明能力不等于获得能力。Loader 验证宿主函数和进程规格，Dispatcher 决定一次调用是否允许执行。

## 13. App 启动与关闭

### 13.1 启动

```text
Load configuration
    ↓
Open and migrate Storage
    ↓
Create Registry / Policy / Dispatcher
    ↓
Create Package Source / Loader
    ↓
Discover and validate Runtime packages
    ↓
Load exactly one valid RoleExecutor when required
    ↓
Create Echo Orchestrator / Scheduler
    ↓
Recover persistent queued Runs
    ↓
Register Access and Service routes
    ↓
Start Web / QQ / Ingress
```

启动失败返回明确错误。缺失 Core 必需依赖时 fail closed，不构造合成配置或匿名身份。

### 13.2 关闭

```text
Stop accepting Web / QQ / Ingress
    ↓
Wait all access admissions
    ↓
Stop external listeners and consumers
    ↓
Cancel active Runs
    ↓
Cancel every queued Run, including delayed attempts
    ↓
Wait Scheduler workers and Run cleanup
    ↓
Stop Agent/Runtime processes
    ↓
Stop background Task Scheduler
    ↓
Flush required state and close Storage
```

关闭顺序由 `internal/app/lifecycle.go` 显式实现。`defer` 只负责启动中途失败时的局部清理，不承担主关闭协议。

## 14. 可观测性

Go 与 Python 使用统一的字段语义和各自的集中日志实现：

```text
request_id
trace_id
app_id
echo_id
run_id
parent_run_id
call_id
capability_id
service_id
tool_id
```

日志、指标、审计分别承担不同职责：

| 类型 | 内容 |
| --- | --- |
| 日志 | 生命周期、稳定错误类别、计数和耗时 |
| 指标 | 低基数状态、成功率、队列深度、预算和延迟 |
| 审计 | 受净化的调用事实、App 范围和保留策略 |

三者都不能记录模型正文、提示词、Tool 参数、Tool 结果、凭据、Cookie、授权头或原始 Provider 响应。

## 15. 测试与 CI

### 15.1 测试层次

```text
Contract tests
  协议、Schema、manifest、lock、错误码

Core unit tests
  状态转换、权限、预算、幂等、child Run、取消、恢复

Adapter tests
  SQLite、Package Source、Runtime Host、gRPC、进程限制

Service/Package tests
  Tool 组合、Capability 行为、独立包构建

Vertical E2E
  Access → Core → Agent/Runtime → Dispatcher → Service → Storage → Event
```

测试替身只实现消费方需要的端口。真实 SQLite/gRPC/Agent E2E 保留一条代表性垂直链路，不为每个入口复制完整系统。

### 15.2 架构约束检查

CI 应检查：

- `internal/kernel` 不 import `internal/services` 和具体 Access 实现；
- `pkg/packagefmt` 不 import Core `internal`；
- `pkg/packmgr` 不 import Core `internal`；
- Service 不直接 import SQLite concrete package；
- Tool 不 import Service；
- Protobuf 生成物与源文件没有 drift；
- Go、Python 和 Package Manager 各自使用锁定的工具链；
- 全量 Go test、race、vet、Python tests 和适用的 integration 门禁通过。

这些检查使用项目已有工具或简单脚本，不引入新的架构框架。

## 17. 迁移计划

每个阶段保持一个可构建、可回滚的提交或 PR。阶段之间不保留两套长期实现。

### 阶段 1：固定公共契约

- 抽出 package、Capability、Executor 的版本化契约。
- 明确 `Package`、`Component`、`Service`、`Tool`、`Runtime` 和 `Executor` 的字段边界。
- 增加 Core/Package/Agent 的 import 约束检查。

### 阶段 2：迁移 packagefmt

- 解除 `pkg/packagefmt` 对 Kernel 私有类型的依赖。
- 将 hosted protocol 复验从作者侧格式层拆出。
- 迁移 `packagefmt`、`packmgr`、`sdkgen` 到 package manager module。
- 在独立 module 中运行作者侧构建和契约测试。

### 阶段 3：解耦 Loader

- Loader 依赖 Package Contract 和 `PackageSource` 端口。
- packmgr 通过 Adapter 提供本地安装和注册表读取。
- Loader 保留自己的信任边界复验。

### 阶段 4：Agent 标准 Package 化

- Python Agent 发布为 `RoleExecutor` Package。
- Go 侧进程代码改成通用 Runtime Host。
- 将 child Run 控制能力归入 Core 的通用 child execution 能力。
- Core 测试只依赖 `internal/kernel/executor` 和 Loader 的通用宿主。

### 阶段 5：拆分组合根

- `cmd/ailuo-core/main.go` 只负责启动。
- `internal/app` 负责依赖装配和生命周期。
- Package Manager CLI 独立于 Core CLI。
- 删除主流程对多个 `defer` 关闭顺序的隐式依赖。

### 阶段 6：收敛 Access 用例

- Web、QQ、Ingress 统一调用 `EchoAdmission`。
- Access 只保留协议、认证、身份、会话和响应适配。
- 保留每个入口独立的 admission gate。

### 阶段 7：按消费者收窄 Store

- 只在出现不同消费者或不同实现时拆 Store 端口。
- 保持 Orchestrator 内部的组合 Store，避免方法级接口碎片化。
- 通过 Adapter contract 测试保证 SQLite、未来数据库实现一致。

### 阶段 8：独立安全和规模演进

- 单独实现 Ingress 机器认证、来源绑定和防重放。
- 取得授权后实现官方校巴数据 ingestion。
- SQLite 达到规模边界后评估 Go-managed PostgreSQL 或其他存储 Adapter。
- 需要事件广播时再评估 Kafka/NATS。

## 19. 验收标准

重构完成需要同时满足：

### 依赖

- Core 编译不需要 Service 源码实现。
- Core 编译不需要 packagefmt、GitHub Client 或 Python Agent 源码。
- packagefmt 在独立 module 中可以解析、提取、构建和测试。
- Agent 在独立 Python module 中可以通过 uv 锁定依赖并实现 executor.v1。

### 运行

- Agent、Campus 和其他 Service 都通过 Package/Component/Loader 模型安装。
- Agent 的 isolated Runtime 没有额外的权限旁路。
- hosted 和 isolated Component 都经过统一 Dispatcher 和 Loader 约束。
- Run Scheduler 只处理持久 queued Run，进程内通知不成为事实来源。

### 状态

- Echo、Run、Task、Confirmation 的状态转换有单一拥有者。
- 创建、claim、retry、cancel、complete 和恢复具备原子性测试。
- child Run 始终由 Go 创建，具备 parent、scope、预算和取消语义。
- 关闭时没有新接入请求能晚于 Scheduler 的 queued 取消。

### 安全

- App、Storage、Event、Audit 和 Capability 查询都按 `app_id` 隔离。
- Package、Runtime、Service 和 Tool 不通过内部调用提权。
- 外部输入、Protobuf、JSON、manifest、lock 和进程参数都严格校验。
- 日志、公共响应和审计不泄露正文、凭据、路径或 Provider 原始响应。

### 工程质量

- 关键依赖方向由 CI 检查。
- 每个重构 PR 只改变一个边界或一个生命周期不变量。
- 相关 Go/Python/integration/race/vet 门禁通过。
- 文档明确区分目标设计、已实现基线、测试证据和剩余阻塞项。

## 20. 决策摘要

```text
Core
  = 治理 + 持久执行 + 调度 + Capability 路由

Agent
  = 实现 executor.v1 的普通 Package/Service

Service
  = 业务 Capability 装配体

Tool
  = 可复用原子能力

Package Manager
  = 分发、安装、升级和作者工具

Loader
  = Package Contract 到 Runtime 的信任边界

Kafka
  = 未来可选的事件基础设施，不是 Core 的事实来源
```

Core 只拥有系统事实和治理规则。Agent、Service、Tool、数据库和包管理器都通过稳定契约接入。
