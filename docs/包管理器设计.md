# AI珞（爱珞）V3 包管理器设计

> 状态：设计稿
>
> 本文固定 AI珞 包管理器的完整契约。定位：**通用、多语言、可被其他系统直接使用的包管理器**（类似 npm 的产品形态）；AI珞 内核是它的第一个宿主消费者，不是唯一消费者。内容覆盖：包格式、无状态规范、版本设计、生命周期、宿主函数投影、**CI workflow 规范**、**多语言支撑**、**鉴权独立性**、工具链。系统装配和当前实现见 `系统架构说明.md`，鉴权边界见 `鉴权与委托授权设计.md`，状态见 `仓库状态与路线图.md`。

## 一、目标与结论

1. **开箱即用**：包管理器是中立产品（包格式 + CLI + 注册表协议 + CI 规范 + SDK 生成）；它不拥有任何消费方的 Loader、数据库或宿主能力。消费方通过稳定包契约安装和使用包，运行时装载与宿主能力由消费方负责。
2. **多语言**：hosted = wasm32-wasi（任何可编译为 wasm 的语言）；isolated = 原生进程 + gRPC（`runtime_host.proto`，任意语言）；分语言 SDK 是主要投入。
3. **包无状态是硬契约**：包实例不持有权威业务状态；权威状态一律在宿主统一存储（AI珞 = Go L1，按 `app_id` 隔离）。实例可销毁重建、崩溃重启、升级迁移而无数据损失。
4. **版本化**：semver + 约束解析 + lock 固定；升级原子切换、旧版本 drain；降级只回滚代码、不回滚数据。
5. **鉴权只属于特定包**：只有涉及智慧珞珈数据/身份/委托 token 的包声明鉴权需求；其他包完全独立。鉴权由宿主（AI珞 内核）强制执行，**包管理器本身无鉴权语义**。
6. **CI workflow 规范**：npm 式发布流水线（构建 → 测试 → 版本 → 打包 → 发布 → 完整性/签名 → 安全扫描），以可复用 workflow 提供给包作者。
7. **安装 ≠ 授权**：包声明的权限只是上限，宿主 App 显式启用并授予后才生效（沿用鉴权设计六）。
8. **宿主函数永远在宿主**：安装包不能自带宿主函数实现；包在 manifest 声明所需宿主函数，宿主按声明投影并校验。
9. **bus 包化是第一个验收**：先统一内置/安装包契约，再把 `campus.bus` 真正放入安装目录。

## 二、现状基线

### 已实现（代码证据）

- Core 统一 Loader（`internal/kernel/loader`）：hosted（wazero 沙箱）/ isolated（进程）两种模式；capability / executor 两种角色；registered → loading → ready → unloading → failed 状态机；注册期按 Verify 绑定唯一宿主；Acquire/Release 在途引用；pin、idle TTL、单飞 Load、Warmup、RecoverFailed、Shutdown drain。
- 安装目录（`internal/adapters/packagesource/catalog.go`，`ailuo.package.v3`）：manifest.json + lock.json（manifest/artifact SHA-256）、严格 JSON、目录属主/权限/符号链接校验、工件 digest 重验、启动全量发现与原子注册（`RegisterInstalled`）。
- 安装 hosted 包：campus（`packages/campus-bus` + 通用 `ailuo.store` 存储宿主函数）；Loader 使用通用 WASM 测试固件验证沙箱边界，不维护内核内业务实现。
- main.go 已接线：`AILUO_RUNTIME_INSTALL_ROOT` 发现 + hosted backend + 安装目录中的 capability/executor 记录同池注册。
- 跨语言线协议已定义：`runtime_host.proto`（Describe/Start/Health/Invoke/Stop，unary gRPC，任意语言可实现 Backend）。
- **阶段 1 地基（2026-08-22，历史契约）**：semver 解析/比较/约束引擎（`semver.go`）；manifest 增加 `host_functions` 与 `storage` 声明并严格校验（`declarations.go`）；宿主函数按包投影——Verify 校验声明 ⊆ 宿主可用集合、Load 校验 guest 导入只属于声明集合（WASI 除外）；内置包与 installed 包统一 `validateRecordSpecs` 校验路径；当时 campus 声明 `ailuo.bus.query` 宿主函数依赖与 `campus/bus` storage 契约，现行包改用通用 `ailuo.store`。
- **分层重构（2026-08-22）**：公共包契约层（现为 `contracts/pkg/packagecontract`，包含 semver、声明、中性清单 `ailuo.package.v3`、lock、进程规格与严格校验）与 `package-manager/pkg/packmgr` 安装/升级/发布实现分离；项目依赖清单与 `ailuo.lock` 校验由 `contracts/pkg/projectcontract` 提供；Loader 只依赖 contracts 与自身运行时校验，宿主扩展段由安装适配器严格解码为 Registry 规格。
- **阶段 2 核心（2026-08-22）**：Loader 原子升级流程 `Manager.UpgradePackage`——候选组件按依赖拓扑加载、全部健康后**组级原子切换**、旧版本在途全部排空后**反序停止**（消费者先停、Provider 后停）；任一候选失败不切换（旧版原样保留）；Shutdown 有界等待退役组件停止。
- **CLI 与发布流水线（2026-08-22）**：`ailuo install/upgrade/uninstall/list/inspect/pack/publish` 落地；`pack` 生成 npm 式 tarball（`<id>-<version>.tgz`），`install` 支持目录/tarball/GitHub Release 源；`publish` 以 GitHub Releases 为分发后端（纯 REST、免 git CLI、版本不可变）；可复用发布 workflow 已在 `.github/workflows/package-publish.yml` 落地（build → 清单 inspect → 必填测试 → tag 校验 → pack → tarball 安装冒烟 → artifact → tag 时 publish → 注册表安装闭环验证）。
- **Package/Component 模型（2026-08-23）**：manifest 重构为 `components[]`（Package=分发/版本/升级单位，Component=运行单元，每组件一种 mode）；`packagecontract.ComponentOrder` 按 imports/exports 拓扑排序并拒绝环；lock 按组件记录工件哈希与进程规格；Catalog 按组件产出内核记录（Capability 按 exports 映射到组件运行时，Service/Tools 路由到包内唯一主能力组件）；`Manager.RegisterPackage`/`UpgradePackage` 落地组编排；`hosted`/`isolated` 命名按约定暂不改。
- **消费方 SDK（2026-08-27）**：`package-manager/pkg/sdkgen` 从 manifest 的 `extensions.capabilities` 严格生成 Go、Python、TypeScript SDK；生成物经编译/导入与真实 HTTP invoke 链路验证，认证和治理 Header 由调用方显式提供。
- **Executor 包工作区（2026-08-31）**：目录工件递归哈希/复制/tar 往返与 isolated 进程模板已实现；`packages/agent`、`packages/campus-bus` 作为同仓包工作区，Core 不再包含具体执行者源码或内置业务包源；执行者专属配置由各自 Deployment 管理。
- **模块边界（2026-09-01）**：`contracts` 与 `package-manager` 是同仓的独立 Go module。Core 仅依赖 `contracts/pkg/capability`、`contracts/pkg/packagecontract`、`contracts/pkg/packageio` 和 `contracts/pkg/projectcontract`；作者工具、安装实现、注册表、SDK 生成器及 `ailuo-pm` CLI 位于 `package-manager`，不进入 Core 启动路径。
- **项目依赖闭包（2026-09-01）**：项目根 `ailuo.toml` 使用 `[dependencies."包 ID"]` 声明显式 `path`/`registry` 来源；`ailuo-pm sync` 递归解析所有传递依赖、检测来源冲突和环、按依赖顺序安装并生成 `ailuo.lock`。Core 只按项目锁装载，不再自由发现安装根中的包。
- **包格式 v3（2026-09-01）**：isolated 组件必须在作者清单显式声明进程模板；移除从 entrypoint 推断进程的旧行为。v2 不再被当前契约接受，包作者通过 `ailuo-pm pack/install` 自动生成和校验安装 lock。
- **进程环境边界（2026-09-02）**：安装 lock 的 `ProcessSpec` 只包含路径、参数、工作目录、本机地址和资源上限；Core 托管 isolated 进程使用空环境，不继承 Core 环境，也不接受包清单中的环境字段。Provider 配置与秘密由组件自己的 Deployment/监督器管理；旧 `env` 字段按严格 JSON 契约拒绝。

### 包管理器边界与后续项

- **Loader 属于消费方**：AI珞 的 `internal/kernel/loader` 负责本身的安全边界和宿主能力；包管理器只输出中性 manifest/lock，不反向依赖 Loader。其他系统可以实现自己的 Loader，不需要引入 AI珞 Core。
- **注册表服务不存在**：当前以 GitHub Releases 为分发后端（REST、不可变版本），自托管注册表仍待外部消费者出现后落地；GitHub Release 已支持项目依赖闭包解析。
- **签名未做**：发布物只有 SHA-256 完整性（manifest/artifact digest 与 tarball 解压校验），无签名。
- **安装目录属主校验**：Unix 使用 UID，Windows 使用 ACL SID；其他平台 fail closed。

## 三、定位：中立基底与宿主

```text
包管理器（中立产品，开箱即用）
├─ 包格式：manifest + lock（语言无关的中性核心）
├─ CLI：sync / inspect / pack / install / upgrade / uninstall / list / publish / sdk-*
├─ 注册表协议：REST（npm 风格：发布 / 下载 / 版本索引 / 完整性）
├─ CI workflow 规范：可复用发布流水线

消费方 Runtime（由消费方实现）
├─ 读取包契约并装载组件
├─ 提供自己的 sandbox / storage / auth 适配器
└─ 经 Dispatcher 或等价治理入口调用 Capability

消费者（不重写装载机制，只接两个小面）
├─ 客户端 SDK：按 capability ID 调用（HTTP `POST /api/v1/capabilities/{capability_id}/invoke`）
├─ 适配器注册：自己的存储/鉴权/身份/宿主函数钩子
├─ AI珞 内核（第一个消费者）：注册 ailuo.store 通用存储、智慧珞珈鉴权等适配器
└─ 未来其他系统：装 SDK + 适配器，开箱即用
```

- **包格式与宿主语义分离**：manifest 中性核心（id、version、language_runtime、abi、entrypoint、artifact、依赖约束、integrity）语言与宿主无关；Tool/Service/Capability、storage、host_functions、权限是 **AI珞 宿主扩展段**，其他宿主可忽略或自行解释。
- **命名保持中立**：工具与格式命名避免品牌绑定（`ailuo` 子命令可更名），不阻碍第三方采用。

## 四、包的定义与形态

### 4.1 Package 与 Component 分离

**Package 是分发、版本与升级单位；Component 是运行单元，每个组件恰好一种运行模式。**
一个包可包含多个组件，通过统一 Capability 通信；只有必须同步发布、升级、回滚的组件
才放进同一个包，能独立演进的应拆成多个包经 Capability 依赖连接。

```jsonc
{
  "schema_version": "ailuo.package.v3",
  "id": "campus.bus",
  "version": "1.2.0",
  "components": [
    { "id": "bus.core", "mode": "hosted", "entrypoint": "bus-core.wasm",
      "exports": ["campus.bus.query"], "imports": ["campus.bus.transport"] },
    { "id": "bus.adapter", "mode": "isolated", "entrypoint": "bus-adapter",
      "exports": ["campus.bus.transport"] }
  ]
}
```

不变量：

1. 一个包可以有多个运行单元，但一个运行单元只能有一种 mode。
2. 组件间通信一律经内核 Dispatcher 路由的 Capability 调用，不直连：wasm 组件调用
   `imports` 中的 Capability 时经宿主函数/内核投影，Host 路由到提供方组件，与提供方
   是 hosted 还是 isolated 无关；提供方在依赖拓扑中先启动、后停止。
3. 全部组件共享包版本；组件版本 = 包版本。
4. 权限按组件分配：wasm 组件不继承 isolated 进程的 OS 权限；数据经 Host Storage
   共享，不共用文件目录。

### 4.2 安装目录形态

```text
<install-root>/<pkg-id>/          # 目录名 = 包 ID（一个包一个目录）
├─ manifest.json                  # 清单（components[] + 包级扩展段）
├─ lock.json                      # 安装锁：包版本 + 每组件工件哈希 + 进程规格
└─ <entrypoint>                    # 每个组件的 entrypoint 工件（清单内的 basename）
```

isolated 组件的安装期 `ProcessSpec` 只描述可执行路径、参数、工作目录、本机地址和资源上限。Core 托管启动时使用空环境；包的 Provider 配置、凭据和其他业务环境由包自己的 Deployment/监督器提供，不进入 manifest 或 lock。

### 4.2.1 项目清单与项目锁

项目根目录另有一组文件，不能与包内 `manifest.json`/`lock.json` 混用：

```text
ailuo.toml                         # 项目直接依赖与来源
ailuo.lock                         # 解析后的完整依赖闭包
```

项目清单使用 `[project]` 和 `[dependencies."package.id"]`：

```toml
[project]
id = "ailuo"

[dependencies."agent"]
version = "1.0.0"
path = "packages/agent"
```

每个依赖必须显式声明 `path` 或 `registry = "github:owner/repo"`。项目锁固定
项目清单摘要、每个包的精确版本、来源、manifest 摘要和路径无关的安装 lock
摘要；Core 重新计算这些摘要，不能把当前安装集合当作解析结果。

### 4.3 清单结构（中性核心 + 宿主扩展段）

- **包级（中性核心）**：`id`、`version`、`components[]`、`dependencies`（包↔包）、
  `pin`、`idle_ttl_ms`、`storage`（经 Host Storage 共享的数据契约）。
- **组件级**：`id`、`mode`（hosted/isolated，命名暂不改）、`entrypoint`（工件）、
  `exports`（提供的 Capability ID）、`imports`（消费的 Capability ID）、
  `host_functions`（wasm 沙箱权利，第二权限轴）。
- **宿主扩展段 `extensions`**：AI珞 的 `tools`/`service`/`capabilities` 定义
  （包级统一接口，组件 exports 引用其 ID），其他宿主忽略。

```jsonc
{
  "schema_version": "ailuo.package.v3",
  "id": "campus.bus",
  "version": "1.2.0",
  "components": [
    { "id": "bus.core", "mode": "hosted", "entrypoint": "bus-core.wasm",
      "exports": ["campus.bus.query"], "imports": ["campus.bus.transport"],
      "host_functions": [{ "module": "ailuo.store", "name": "list" }] }
  ],
  "storage": { "namespace": "campus/bus", "schema_version": 1,
               "sensitivity": "public", "retention": "permanent" },
  "extensions": { "tools": [...], "service": {...}, "capabilities": [...] }
}
```

### 4.4 双权限轴（不混为一个）

1. **Capability 级 authZ（第一轴）**：每个 Capability 的 `required_permissions`，
   逐调用经 Dispatcher 校验（现有模型，不改）。
2. **沙箱权利（组件级，第二轴）**：wasm 组件的 `host_functions` import 集；
   isolated 组件的 OS 资源限额/进程规格。第二轴只决定"组件在沙箱里能碰到什么"，
   不替代第一轴的逐调用授权——wasm 组件绝不继承 isolated 组件的进程级权利。

### 4.5 运行层抽象（RuntimeDriver）

运行层统一抽象 `RuntimeDriver`（即现有 Loader 的 `Host`/`Runtime` 契约，命名固化）：
`Verify`、`Prepare`（Load）、`Start`、`Health`、`Invoke`、`Stop`。

- **WasmDriver**（hosted）：wazero 主进程内沙箱，启动快、跨平台、默认禁止文件与
  网络访问，适合文本处理、数据转换、普通校园查询等社区包。
- **ProcessDriver**（isolated）：Unix 使用本机 Unix Socket，Windows 使用回环 TCP 上的 gRPC，适合
  Python AI、OCR、浏览器自动化、原生 SDK 等重型能力；仅限官方或可信发布者
  （依赖签名机制，阶段 3 落地前由"安装属受信操作"兜底），并施加 OS 级资源与权限限制。

两种驱动共用统一 Manifest、Capability ID、JSON Schema、权限声明、依赖规则与版本
规范，不形成两套包生态；Agent 与上层业务只调用 Capability，无需感知背后语言或运行方式。

## 五、无状态规范（核心原则）

1. **实例无权威状态**：包实例（Runtime）不保存跨调用权威状态；内存缓存可随时丢弃；实例重启、重建、迁移、升级不丢数据。权威状态一律经 storage 声明落宿主存储（AI珞 按 `app_id` 隔离）。
2. **凭据不落入包**：包不持有数据库凭据、第三方 token、秘密；hosted 组件需要外部能力时经宿主函数投影，isolated 组件由自身 Deployment 按批准的秘密源提供，Core 与包管理器都不注入。
3. **崩溃语义**：实例崩溃 → 宿主标 `failed` → `RecoverFailed` 重建新实例；在途调用有界失败，已持久化状态不受影响。
4. **幂等与重放**：写类 Tool 必须声明幂等键语义，重放安全（沿用 `internal/kernel/idempotency`）。
5. **存储访问**：业务数据经声明的 storage 端口/宿主函数读写；App 隔离在宿主侧强制（guest 无法伪造 `app_id`）。
6. **禁止项（Verify 与审计拒绝）**：包内自建私有库、包把用户状态留在进程内、包绕过宿主创建不可治理的持久任务；Executor 的进程内递归不改变其当前 Run 的治理边界。

验证：实例重启/升级后状态一致测试；崩溃恢复测试；跨 App 隔离测试。

## 六、版本设计

### 6.1 版本号：semver 2.0

- `MAJOR.MINOR.PATCH`（可选 `-pre` / `+build`）。包内全部规格与 runtime 同版本（现有校验已强制）。
- 版本号是包的**公共契约**：对宿主、App 配置、lock、审计均可见。

### 6.2 兼容性语义

| 变更 | 示例 | 行为 | 治理 |
|---|---|---|---|
| patch | 1.0.0 → 1.0.1 | 仅修复；schema、语义、权限不变 | 热替换；无需宿主确认 |
| minor | 1.0.0 → 1.1.0 | 向后兼容新增：新 Tool/Capability、可选参数 | 现有契约不变；**新 Capability 默认不进任何 App**，需宿主控制面显式启用 |
| major | 1.x → 2.0.0 | 破坏性：schema、语义、权限、存储 schema 变更 | 宿主控制面显式确认（generation CAS）；可能伴随存储迁移 |

### 6.3 版本约束与解析

- 约束语法：精确 `1.2.3`；caret `^1.2.0`（≥1.2.0 且 <2.0.0）；范围 `>=1.0.0,<2.0.0`。
- 解析时机：`ailuo sync` 从项目直接依赖开始递归读取包清单，按显式来源解析完整传递闭包；同一包出现不同来源、约束冲突或依赖环时 fail closed。解析成功后按依赖拓扑安装，并写入项目 `ailuo.lock`（精确版本 + manifest 摘要 + 路径无关安装 lock 摘要）。
- **版本唯一性**：同一宿主内同一 `tool_id` / `capability_id` 只允许一个已发布版本；升级是版本替换，不做多版本并行（避免路由歧义；有明确需求再放宽）。
- 冲突：同一包的来源或版本约束不可同时满足 → fail closed；不得从已安装集合静默选择替代版本。

### 6.4 升级与降级（以 Package 为单位）

升级以整个包为单位，组件作为组编排：

1. 校验全部组件清单与权限（第一轴 + 第二轴）；
2. 按依赖拓扑启动候选组件（通常先启动 isolated Provider，再启动依赖它的 wasm 组件）；
3. 全部组件健康后，**原子切换整个包**（切换只是指针替换，无部分失败）；
4. 旧版本按依赖反序 drain（`in_flight` 归零后，消费者先停、Provider 后停）；
5. 任一候选组件失败 → **不切换**（旧版本原样保留，可回滚）；切换后的运行时故障是
   显式降级操作，不是升级的一部分。

- **minor/patch 升级**：候选组全绿后原子切换；宿主配置与 Run 状态不受影响。
- **major 升级**：宿主控制面显式确认；存储迁移前向执行成功后激活；失败保留旧版本。
- **降级**：仅工件/代码回滚到 lock 上一版本；存储 schema 只前向，不自动回滚数据。
- **升级不扩权**：新增 permissions 不自动进入既有 App（鉴权设计 6.2）。
- 升级全程幂等；失败保留旧句柄供 Shutdown 清理。

## 七、多语言支撑

| 运行模式 | 语言 | ABI | 现状 |
|---|---|---|---|
| hosted | 可编译 wasm32-wasi：Rust、Go(tinygo)、C、AssemblyScript 等 | stdin/stdout JSON 信封 + 宿主函数 import | wazero 沙箱已实现；测试使用通用 WASM 固件 |
| isolated | 任意语言（Python/Go/Rust/...） | `runtime_host.proto` gRPC unary | 协议、监管、进程规格已实现 |

- **per-language SDK（新增，主要投入）**：`ailuo-sdk-go` / `ailuo-sdk-rust` / `ailuo-sdk-python` / `ailuo-sdk-ts`，提供统一 Host API（`ctx.storage`、`ctx.http`、`ctx.identity` 等）与信封编解码、schema 助手、生命周期骨架——作者只实现 Capability，不直接处理 WASM 内存或 gRPC 生命周期；SDK 与 CLI 共享同一契约定义，避免各语言漂移。V1 用 JSON Schema 描述接口、Protobuf 管理控制面、JSON 信封承载调用；未来 WIT 工具链成熟后再迁移强类型接口。
- **`ctx.http` 是 SSRF 高危能力**：wasm 沙箱默认无网络，`ctx.http` 由内核代包发请求，必须限定目标（域名 allowlist、拒绝内网 IP、超时/重试/审计）；`ctx.storage` 相对安全（宿主侧隔离强制）。
- **能力差异**：wasm 无文件系统/网络（WASI 裁剪）→ 需要内核能力必须走宿主函数；isolated 进程可自行访问网络，但 Provider 配置和凭据不由包管理器或 Core 注入，需由组件自己的 Deployment/监督器提供。
- 契约中立性：SDK、信封、gRPC 定义均不引用 AI珞 业务语义，其他宿主可复用。

## 八、宿主函数投影（host function）

- 宿主维护**宿主函数注册表**：`module.name → 实现`（AI珞 内核 Go 代码，受信计算基）。当前实例是通用 `ailuo.store`（get/list/put/delete：namespace 绑定包声明、App 隔离宿主强制、快照元数据内嵌单事务一致读）；按包定制的宿主函数已随 `pkg/bus` 移除，新增有状态包零内核改动。
- 包 manifest 声明所需宿主函数；**Verify 时**校验注册表包含；**Load 时**只投影声明集合（wasm 侧只 import 声明的 module/name，未声明调用直接拒绝）。
- 内置包与安装包共用同一注册表与投影校验。
- 通用宿主函数能力面（`storage.*`、`observe.*`、`identity.*` 等）作为逐步投影候选，每个都有闭式协议、App 隔离强制与泄露负向测试。
- **中立性**：宿主函数是 AI珞 宿主能力，不是包格式的一部分；不依赖它们的包（无 host_functions 声明）可在任何宿主/独立环境运行。

## 九、CI workflow 规范（npm 式发布流水线）

包作者仓库的标准发布流水线，以**可复用 workflow**（GitHub Actions `ailuo-package-publish` 等）形式提供，各包仓库 `uses:` 即得。调用方必须传入 Package Manager 仓库、不可变 `package-manager-ref` 和 `test-command`；workflow 先由 `ailuo-pm inspect` 读取 `ailuo.toml` 的组件构建计划，再按声明准备工具链，不重复维护构建器参数，也不绑定某一种语言或业务包：

| 阶段 | 内容 | 产出/校验 |
|---|---|---|
| 构建 | 按 `ailuo.toml` 的 `[component.build].tool` 构建（WASM 交叉编译 / 原生构建）；依赖版本由各语言 lock 管理 | 可复现工件 |
| 测试 | 单元测试 + 对宿主 substrate 的集成测试（wasm 信封 golden、gRPC 契约） | 测试证据 |
| 版本 | semver 由 conventional commits 或显式 tag 决定；校验 `manifest.version` 与 git tag 一致 | 版本一致 |
| 打包 | 生成 manifest + lock + artifacts + integrity（SHA-256）；lock 固定每组件文件/目录工件哈希与 isolated 进程规格 | 完整安装目录 |
| 发布 | 推送注册表（注册表鉴权只认证包作者，**与智慧珞珈无关**）；SLSA provenance（后续）；签名（预留） | 不可变版本 |
| 安全 | 依赖漏洞扫描、secret 扫描、工件哈希复核 | 通过门禁 |

- 当前内置构建器的工具链映射为：`go-wasm` 使用调用方 Go module 的 Go，`go-native` 构建调用方目标平台的原生进程，`python-uv` 使用 uv，`ts-as` 使用 Node/npm；未知构建器在 `inspect`/`pack` 阶段 fail-closed。构建由 `ailuo-pm pack` 根据包清单执行，workflow 不接受或执行额外的调用方 build command，避免同一工件被重复构建。
- 新语言应先新增包格式构建器和对应的工具链适配，再扩展这份通用 workflow；不得把某个 Agent、Campus 或其他业务包的逻辑写进发布流程。

- 可复用 workflow 的 `test-command` 是必填发布前门禁；`package` job 输出已验证发布物的 `artifact-id`，发布 job 只下载该 artifact，不执行调用方构建命令。
- **不可变版本**（npm 式）：注册表已发布版本不可覆盖；错误版本通过新版本修复。
- 发布是受信操作（CI 角色/控制面），与运行期调用鉴权无关。
- 门禁：包作者 PR 必须通过 CI 才能发布；发布事件全审计（包 ID、版本、发布者、结果）。

## 十、鉴权独立性

### 10.1 两个鉴权面（均服务端统一）

| 鉴权面 | 作用 | 归属 |
|---|---|---|
| 注册表鉴权 | 包发布者/下载者身份认证（npm 式），与智慧珞珈无关 | 注册表服务端统一处理 |
| 运行时鉴权 | 每次调用的身份解析 + 授权校验 | 经宿主能力适配器契约在服务端统一执行；AI珞 三层鉴权是参考实现，其他系统通过同一适配器接口接入自己的策略引擎 |

- 接口统一、策略归消费者：适配器契约（身份解析、授权检查、审计回调）由中立运行时定义；AI珞 的 `鉴权与委托授权设计.md` 三层模型是其实现之一，不是唯一实现。
- 包管理器不实现具体鉴权策略；具体策略永远在服务端（消费者/宿主侧），客户端与包不可绕过。

### 10.2 智慧珞珈范围

- 只有涉及智慧珞珈数据/身份/委托 token 的包，在 manifest 声明对应宿主函数（如未来 `ailuo.luojia.*`）与权限需求 → AI珞 宿主按 `鉴权与委托授权设计.md` 三层模型强制执行。
- **其他包完全独立**：工具类、公开数据、纯计算包不声明任何鉴权需求，可在任何宿主/独立环境运行；智慧珞珈的接口、SSO、委托 token 对它们不存在。
- 边界：声明 `ailuo.luojia.*` 宿主函数的包只能运行在提供该能力面的 AI珞 宿主；未声明的包与宿主无关。
- 数据接入模式 A（机构授权）/模式 B（用户委托）只作用于智慧珞珈数据包，不扩散到整个包生态。

## 十一、bus 包化（第一个验收）

### 11.1 现状

`campus` 是经独立包仓库发布、由安装目录装载的 hosted 包：guest 自包含（只依赖标准库），经通用 `ailuo.store` 宿主函数读写宿主统一存储；数据权威元数据与文档存储由内核 `internal/kernel/packstore` 窄端口 + SQLite/内存实现承载。测试数据由 `testsupport/campus` 经同一端口播种，生产启动不加载 Demo。安装清单由 `ailuo pack` 从作者侧 `ailuo.toml` 生成。

### 11.2 目标形态（两步）

**步骤 1：契约统一（历史基线，已由步骤 2 取代）**

- 历史 manifest 曾增加 `storage`（`campus/bus`、schema_version）与 `host_functions`（`ailuo.bus.query`）声明；现行包使用通用 `ailuo.store` 的声明子集，namespace 仍为 `campus/bus`；
- 宿主函数注册表 + 按包投影校验接入 campus（测试装配与安装包走同一路径）；
- 依赖约束化：`ToolDependencies` 升级为带版本约束。

**步骤 2：真正安装（安装目录包）**   ✅ 已完成

- `campus` 工件 + manifest + lock 由 `packages/campus-bus` 的清单和工具链生成（Package Manager CLI 的 `ailuo-pm pack` 经 `[component.build]` 自动编译）并放入安装目录；CLI 可通过 `AILUO_PACKAGE_INSTALL_ROOT` 或 `--root` 指定安装根，Core 通过 `AILUO_RUNTIME_INSTALL_ROOT` 配置发现根，二者缺省都为用户配置目录 `ailuo/runtime`。内核启动发现、校验、注册、装载与任何安装包一致（安装目录 hosted 包声明 host_functions 时由进程内 WasmHost 装载，宿主函数是内核特权，跨进程无法投影）。
- `pkg/bus` 中立包（2026-08-24 引入，**2026-08-30 移除**）：guest 自包含化后该包失去存在意义。guest 只 import 标准库，领域模型与治理逻辑全部在包仓库内；内核侧持久化统一走 `internal/kernel/packstore` 端口（`ailuo.store` 宿主函数背后）。
- 内置 `campus.Record()`/`campus.Host(store)` 生产路径移除：campus 不再内置，所有环境从安装目录装载；Core 不要求任何具体能力包，只在缺少唯一 Executor 时拒绝就绪。Core 测试只使用通用运行时固件，不维护无业务价值的示例 Package。
- 安装目录属主校验已支持 Unix UID 与 Windows ACL SID；其他平台仍 fail-closed。
- Demo 数据只作为**测试夹具**（非权威、显式标记、不进入生产启动）；生产数据仍经授权 ingestion 写入统一存储；卸载/升级不丢存储数据（存储归宿主，包只声明不持有）。

### 11.3 边界

- guest 业务逻辑自包含在包仓库（只依赖标准库，不依赖内核 `internal/` 与 Core 仓库任何包）；持久化经通用 `ailuo.store` 宿主函数，作用域强制为（App × 包 namespace），数据新鲜度/权威性治理在 guest（读取响应内嵌单事务一致的快照元数据）。宿主把包错误转换为通用 Runtime Invocation 错误，Core 不识别包的领域错误类型。
- 新增**有状态包零内核改动**：包声明 `[storage]` namespace 与 `ailuo.store` 函数子集即可持久化；快照原子替换（`ReplaceSnapshot`）仅对可信 Go 侧开放，供未来授权 ingestion（学校 API OAuth 后写入）使用。
- 校车、校历等后续校园包复用同一包化路径，各自独立安装/升级。

## 十二、权限、治理与可观测性

- **安装 ≠ 授权**：包注册进宿主 Registry 不等于任何 App 可用；App 显式启用并收窄 permissions（鉴权设计六，不改）。
- **控制面/CI 专属**：安装、升级、卸载、发布属于受信控制面（9178 loopback admin + 运维 CLI + 发布 CI），普通用户与 Agent 不可触发；操作全审计。
- **签名预留**：当前保持 SHA-256 锁定；manifest 预留 `signature` 字段，密钥分发方案落地后启用（先哈希后签名，不破坏既有安装目录）。
- **可观测性**：沿用现有 Loader metrics（load/stop/调用数/耗时）；补包版本、升级事件、拒绝投影等低基数标签；包正文、参数、结果不进普通日志（现有净化规则）。

## 十四、作者侧显式清单

### 14.1 唯一源格式

每个可打包目录必须在根部提供 `ailuo.toml`。包管理器不从目录名、源码函数或文件布局推断包 ID、版本、Capability、Schema 或构建器，也不提供无清单回退。

清单至少声明 `[package]`、一个 `[[component]]` 和每个需要构建的组件的 `[component.build]`。Capability 的输入 Schema、权限与副作用显式写入清单；`packagefmt` 只在同一份 TOML 内执行有限的字段继承，不能替代契约声明。`isolated` 组件还必须显式声明 `[component.process]`，至少给出启动路径；参数和工作目录可省略，由安装器使用工件根目录的确定性默认值；Unix 的本机地址可省略并生成包内绝对 Unix Socket，Windows 必须显式提供回环 TCP 地址，不能生成不受支持的 Unix Socket。进程模板和安装锁均不包含环境变量、Provider 配置或秘密；`mode=isolated` 只表示隔离边界，不能让包管理器猜测启动方式。发布归档的 `lock.json` 绑定相对工件摘要；安装时由 `packmgr` 自动重新生成绝对路径 lock，并固化该进程规格，部署者不需要手工改 lock。

### 14.2 构建器

| 构建器 | 源码 | 命令 | 前提 |
|--------|------|------|------|
| `go-wasm` | `main.go` | `go build -trimpath -o main.wasm .`（GOOS=wasip1） | Go 工具链（门禁既有前提） |
| `go-native` | Go module 源码目录 | `go build -trimpath -o <entrypoint> .` | Go 工具链 |
| `python-uv` | Python 项目目录 | `uv sync --locked --no-dev` | uv 与 `uv.lock` |
| `ts-as` | `main.ts`（AssemblyScript 语法） | `npx --yes --package assemblyscript@0.27.31 asc main.ts -o main.wasm` | node/npx |

- hosted 调用契约为 WASI stdin 信封 + stdout 结果信封 + `_start` 入口（WasmHost 强制）；guest 必须自行实现该入口。
- stdout 结果信封只能是严格 JSON：成功为 `{"ok":true,"result":<json>}`，失败为 `{"ok":false,"code":"<code>","message":"<optional-detail>"}`；`code` 只能是 `data_unavailable`、`data_incomplete`、`data_expired`、`data_untrusted` 或 `invalid_argument`、`internal`，`message` 可省略但出现时必须是非 null 字符串。顶层键必须使用精确小写名称，不得有未知/重复键、尾随内容或混用 `result` 与错误字段。成功必须提供 `result`，失败必须提供非空 `code`。

### 14.3 生成流程

```
ailuo.toml
  → packagefmt.Parse（严格 TOML + 中性 Manifest + BuildSpec）
  → [component.build] 构建
  → packmgr 打包（manifest.json + 归档 lock.json + 工件摘要）
  → install / projectmgr sync
  → Core 按 ailuo.lock 验证并装载
  → sdkgen 从已声明 extensions 生成消费方 SDK
```

## 十五、消费方 SDK（契约生成）

### 15.1 设计原则

- 从包清单的 `extensions` 段（tools/service/capabilities + JSON Schema）**自动生成**各语言 SDK，不保留手写 SDK 或兼容回退。
- 生成的 SDK 仅用标准库，不依赖内核 `internal/` 包，可被外部项目直接 `go get` 复用。
- 一个生成入口（`package-manager/pkg/sdkgen.Generate`），跨语言 emitter（Go + Python + TypeScript）。

### 15.2 类型派生规则

| JSON Schema | Go | Python | TypeScript |
|-------------|----|--------|------------|
| `string` | `string` | `str` | `string` |
| `integer` | `int64` | `int` | `number` |
| `number` | `float64` | `float` | `number` |
| `boolean` | `bool` | `bool` | `boolean` |
| `string` + `format:date-time` | `time.Time` | `datetime` | `Date` |
| `string` + `enum` | 具名 type + const | class(str, Enum) | string literal union |
| `array` + `items` | `[]T` | `list[T]` | `T[]` |
| `object` + `properties` + `additionalProperties:false` | 具名 struct | `@dataclass` | `interface` |

非必填标量与对象字段 → 指针（`*T`/`Optional[T]`/属性级 `?`）；Go 非必填数组 → `*[]T`，区分未提供与显式空数组；整数 `enum` 在生成前即被拒绝（`KindEnum` 只承载字符串）。

### 15.3 传输层信封

- 端点：`POST /api/v1/capabilities/{capability_id}/invoke`
- 请求：`{"input": <payload>}`（严格解码，禁止未知字段 / 尾随内容）
- 响应：`{"capability_id": "...", "result": <value>}`
- 治理（App 策略、权限收窄、Schema 校验、幂等/确认）由内核 Dispatcher 统一执行，HTTP 层只做信封与鉴权。
- 认证：生成客户端提供调用方 Header/认证材料注入点；认证失败不会降级为匿名身份。
- 治理 Header：副作用调用使用 `Idempotency-Key`，已批准确认使用 `X-Confirmation-ID`；两者由调用方显式传入。
- 稳定错误映射：`400 invalid_input`/`invalid_idempotency_key`、`401 authentication_required`、`403 permission_denied`、`404 capability_not_found`、`409 idempotency_conflict`/`confirmation_required`、`503` 受治理数据状态、`504 deadline_exceeded` 等（不泄露内部细节）。

### 15.4 现在与未来

- 已实现 emitter：Go（方法 + 类型化 struct）、Python（函数 + 类型化 dataclass）、TypeScript（`Client` class + `interface`，async/await + fetch），均经可编译/导入验证（Go `go build`、Python `compileall`、TypeScript `tsc --strict`）。
- 契约模型独立于内核 internal 包；当前同仓 module 可独立构建，待 `package-manager` 仓库发布后第三方再通过 `go get` 复用 SDK 生成器。
- WIT 工具链迁移（本设计文档所述未来项）从 `package-manager/pkg/sdkgen` 的 JSON Schema 派生模型演进，不推翻当前契约。

## 十六、实施路线

1. **阶段 1（契约与投影）**：manifest 中性化（核心 + 宿主扩展段）；宿主函数注册表与按包投影校验；内置/安装包统一校验路径；bus 包化步骤 1。
2. **阶段 2（版本与生命周期）**：semver 约束解析器与 lock 生成；升级/降级流程（原子切换 + drain）；major 升级的宿主确认与存储迁移挂钩；`ailuo` CLI 基础（install/upgrade/uninstall/list）。
3. **阶段 3（发布与 CI）**：CI workflow 规范与可复用发布流水线；`ailuo-pm publish`；注册表协议 v1（REST）；签名。
4. **阶段 4（生态）**：扩展 per-language SDK（当前已实现 Go/Python/TypeScript 生成器）；更多通用宿主函数能力面；注册表服务与外部宿主接入。

## 十七、验收清单

- 无状态：实例重启/升级/崩溃恢复后权威状态一致；包内建库、持凭据、留用户状态被 Verify/审计拒绝。
- 版本：semver 约束解析正确；lock 固定可复现；冲突 fail closed；升级原子切换；降级不回滚数据。
- 投影：包声明外调用宿主函数被拒绝；内置/安装包同校验路径。
- 多语言：同一包格式由 wasm（hosted）与 gRPC（isolated）两种语言通路装载；SDK 与 CLI 契约一致。
- 消费方 SDK：一份契约生成 Go/Python/TypeScript SDK（唯一路径，无手写/回退）；生成的 Go 与 TypeScript SDK 可编译且经真实端点调用真实 capability 返回正确结果；Python SDK 通过 compileall 并经真实端点端到端验证。
- 显式源清单：所有可发布包必须提交 `ailuo.toml`；缺少清单、构建器或 Capability Schema 时 `pack`/`publish`/`sdk-*` 直接失败，不根据源码猜测契约。
- CI：包作者仓库接入可复用流水线后可完成构建→测试→版本→发布；不可变版本；发布审计。
- 鉴权独立性：智慧珞珈数据包声明 `ailuo.luojia.*` 依赖并经宿主鉴权；无鉴权声明的包独立运行。
- bus 包化：`campus` 可安装/升级/卸载；卸载不丢存储数据；Demo 仅存在于测试夹具，不进入生产启动。
- 治理：安装 ≠ 授权；升级不扩权；控制面/CI 操作全审计；签名预留不破坏既有目录。
- 门禁：新增功能覆盖对应 Go/Python 测试，跑完整门禁（AGENTS.md Validation）。
