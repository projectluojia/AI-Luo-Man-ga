# AI珞 V3 Package Manager 设计

> 状态：与当前 `contracts`、`package-manager` 和 Core Loader 对齐。公共包模型只有
> Package、Component、Capability；运行角色只有 Provider、Executor。

## 一、职责边界

`contracts` 是可独立发布的公共契约层，定义：

- `manifest.json` / `lock.json` 的格式与严格校验；
- Package 依赖、来源和 semver 约束；
- Component mode、role、工件、进程规格、宿主函数声明；
- Package 的 Capability 规格和导出绑定；
- 项目 `ailuo.toml` / `ailuo.lock` 的完整依赖闭包。

`package-manager` 只负责作者源清单解析、构建、打包、安装、升级、卸载、发布和 SDK
生成。Core 只消费 `contracts` 与 Loader 端口，不导入作者侧实现或发布后端。

## 二、清单模型

作者侧 `ailuo.toml` 的最小 Provider 示例：

```toml
[package]
id = "campus"
version = "1.0.0"

[[component]]
id = "bus"
mode = "hosted"
role = "provider"
entrypoint = "campus.wasm"
exports = ["campus.bus.routes.list"]

[[capability]]
id = "campus.bus.routes.list"
name = "列出校巴线路"
description = "List authoritative campus bus routes."
schema = """{\"type\":\"object\",\"additionalProperties\":false}"""
side_effect = "read"
```

Executor 使用同一 Package/Component 清单，只把 Component role 声明为 `executor`，并
通过 `executor.proto` 实现 Run 协议。一个 Package 可以包含多个 Component；每个组件只
有一个 mode 和一个 role。

Capability 规格直接写入 `Manifest.Capabilities`，Component `exports` 只引用其 ID。
当前 V3 的 Capability version 与 Package version 保持一致，先保证整体发布和回滚的
确定性；未来若需要独立 API 演进，再在契约中显式增加版本约束，不通过隐式兼容处理。
清单校验保证每个声明的 Capability 恰好导出一次，每个导出的 ID 都有完整规格；不会
存在“已生成 SDK 但运行时无法路由”的孤立声明。

## 三、安装与锁定

当前包格式为 `ailuo.package.v3`。安装过程：

1. 严格读取清单，拒绝未知字段、重复键、非法 ID、非法 Schema 和越界字段。
2. 校验每个 Component 工件，拒绝符号链接、路径逃逸、basename 冲突和大小越界。
3. 对 isolated Component 将相对进程模板解析为 lock 固化的绝对 ProcessSpec。
4. 在安装根同级构造完整候选闭包，保存清单摘要、工件摘要和进程规格；
   所有候选通过后才整体切换安装根。
5. 切换后重写绝对路径并重新读取验证；项目锁写入失败恢复上一完整安装，
   不静默覆盖同版本不同内容。

项目级 `ailuo.lock` 固定完整依赖闭包、精确版本、来源、manifest 摘要和安装 lock 摘要。
已有项目锁时优先复用满足当前约束的精确版本；只有新增依赖、约束不再满足或来源改变
时才重新选择版本，同来源同版本的内容摘要变化直接失败。同步先在安装根同级构造
完整候选闭包，所有包验证通过后再整体替换安装根。
Core 只按项目锁发现包，不扫描安装根中额外目录。每个依赖都必须有显式 `path:` 或
`github:` 来源；来源冲突、版本冲突、闭包缺失和依赖环均拒绝。

### 算法取舍（参考 Cargo 与 Pacman）

这里借鉴成熟包管理器的边界和不变量，不直接复制它们面向操作系统/语言生态的实现：

- **Cargo 式 lock-first**：普通 `sync` 先复用 `ailuo.lock` 中仍满足约束的精确版本；
  只有显式 `--update` 才重新选择版本。求解结果按稳定 ID 排序，项目锁保存来源、
  manifest 摘要和安装 lock 摘要，避免“同版本重新下载后内容悄悄变了”。
- **Pacman 式事务发布**：安装、升级、卸载和项目同步都先取得安装根的进程内锁与
  跨进程锁；候选闭包写入临时目录，校验通过后才切换。切换前写事务日志，崩溃后按
  日志恢复旧安装根；旧版本不会先删除而留下半套闭包。
- **不可变发布物**：同一 Package ID + Version 的 manifest 或工件摘要不同就拒绝
  覆盖；发布端同一 Release 版本也不可重复发布。安装 lock 的绝对路径只服务于
  当前部署，项目 lock 使用规范化摘要，因此安装根迁移不会改变依赖身份。
- **显式故障恢复**：跨进程锁使用独占创建。正常退出删除锁；崩溃留下的锁不会依据
  PID 或时间自动删除，因为无法证明持有者已经退出。确认所有包管理进程停止后，
  才允许执行 `ailuo-pm unlock --force --root <安装根>` 清理遗留锁，再由下一次
  `sync` 处理事务日志。

当前实现暂不引入 Cargo registry index、全局 content-addressed 下载缓存、增量解压、
签名信任链或多版本并存。这些能力会改变分发与信任模型，应在出现多个 registry、
重复下载的实测瓶颈或签名发布方后分别引入；在此之前，摘要校验、锁优先和原子事务
已经覆盖当前单 Deployment 的主要一致性风险。

## 四、依赖语义

- Package 依赖：构建/安装/升级关系，按来源与 semver 求解，必须是 DAG。
- Runtime 组合：运行期按 Capability ID 经 Core Dispatcher 消费，不在组件间建立私有直连。
- 普通语言库：由 Go/Python/其他语言自己的构建依赖管理，不注册为 Runtime。

不能用运行期发现替代 lock，也不能通过私有地址建立包间旁路。需要独立权限、数据或
生命周期的实现才作为 Provider Component；Executor 只通过 Core 消费被投影的 Capability。

## 五、Loader 与升级

Catalog 从安装包得到每个 Component 的 Runtime 记录，并把 Capability 按 `exports`
绑定到对应 Runtime。Registry 只保存 Capability；Loader 只保存 Component Runtime。
注册、宿主选择、Schema 编译和冲突检查完成后才进入可调用状态。

Package 升级以整个 Package 为单位：所有候选 Component 按依赖顺序加载并健康后整体切换；
旧版本的在途调用排空后按依赖反序停止。任一候选失败，旧版本保持不变。Provider 与
Executor 使用同一 Loader 生命周期，只有调用面不同。

## 六、授权与 SDK

安装不等于授权。Package 声明能力和最小权限只是上限；App 必须通过受信控制面显式
启用 Capability，默认集合不自动扩张。Dispatcher 在 Go 信任边界重新校验 Schema、
权限、deadline、幂等和确认，并写入 App 隔离审计。

`sdkgen` 输入是 Capability 规格 JSON 数组，生成自包含的 Go、Python 或 TypeScript
客户端。生成器不读取 Core internal，不保留手写客户端或旧格式 fallback。
