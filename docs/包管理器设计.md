# AI珞（爱珞）V3 包管理器设计

> 状态：设计稿
>
> 本文固定 AI珞 包管理器的完整契约。定位：**通用、多语言、可被其他系统直接使用的包管理器**（类似 npm 的产品形态）；AI珞 内核是它的第一个宿主消费者，不是唯一消费者。内容覆盖：包格式、无状态规范、版本设计、生命周期、宿主函数投影、**CI workflow 规范**、**多语言支撑**、**鉴权独立性**、工具链。配套 `v3_overall_design.md`（八）、`鉴权与委托授权设计.md`（六）、`仓库状态与路线图.md`（Loader 基线）。

## 一、目标与结论

1. **开箱即用**：包管理器是中立产品（包格式 + CLI + 注册表协议 + CI 规范 + **中立运行时**），复杂度只实现一次、随产品交付；其他系统通过客户端 SDK 接入中立运行时并注册自己的宿主能力适配器，**不重写装载机制**。
2. **多语言**：hosted = wasm32-wasi（任何可编译为 wasm 的语言）；isolated = 原生进程 + gRPC（`runtime_host.proto`，任意语言）；分语言 SDK 是主要投入。
3. **包无状态是硬契约**：包实例不持有权威业务状态；权威状态一律在宿主统一存储（AI珞 = Go L1，按 `app_id` 隔离）。实例可销毁重建、崩溃重启、升级迁移而无数据损失。
4. **版本化**：semver + 约束解析 + lock 固定；升级原子切换、旧版本 drain；降级只回滚代码、不回滚数据。
5. **鉴权只属于特定包**：只有涉及智慧珞珈数据/身份/委托 token 的包声明鉴权需求；其他包完全独立。鉴权由宿主（AI珞 内核）强制执行，**包管理器本身无鉴权语义**。
6. **CI workflow 规范**：npm 式发布流水线（构建 → 测试 → 版本 → 打包 → 发布 → 完整性/签名 → 安全扫描），以可复用 workflow 提供给包作者。
7. **安装 ≠ 授权**：包声明的权限只是上限，宿主 App 显式启用并授予后才生效（沿用鉴权设计六）。
8. **宿主函数永远在宿主**：安装包不能自带宿主函数实现；包在 manifest 声明所需宿主函数，宿主按声明投影并校验。
9. **bus 包化是第一个验收**：先统一内置/安装包契约，再把 `campus.bus` 真正放入安装目录。

## 二、现状基线

### 已实现（代码证据）

- 统一 Loader（`internal/kernel/loader`）：hosted（wazero 沙箱）/ isolated（进程）/ embedded 三种模式；capability / executor 两种角色；registered → loading → ready → unloading → failed 状态机；注册期按 Verify 绑定唯一宿主；Acquire/Release 在途引用；pin、idle TTL、单飞 Load、Warmup、RecoverFailed、Shutdown drain。
- 安装目录（`internal/adapters/packagesource/catalog.go`，`ailuo.package.v2`）：manifest.json + lock.json（manifest/artifact SHA-256）、严格 JSON、目录属主/权限/符号链接校验、工件 digest 重验、启动全量发现与原子注册（`RegisterInstalled`）。
- 安装 hosted 包：campus（独立包仓库 + 通用 `ailuo.store` 存储宿主函数 + demo 播种）；Loader 使用通用 WASM 测试固件验证沙箱边界，不维护无业务价值的参考 Package。
- main.go 已接线：`AILUO_RUNTIME_INSTALL_ROOT` 发现 + hosted backend + campus/agent 与 installed 记录同池注册。
- 跨语言线协议已定义：`runtime_host.proto`（Describe/Start/Health/Invoke/Stop，unary gRPC，任意语言可实现 Backend）。
- **阶段 1 地基（2026-08-22）**：semver 解析/比较/约束引擎（`semver.go`）；manifest 增加 `host_functions` 与 `storage` 声明并严格校验（`declarations.go`）；宿主函数按包投影——Verify 校验声明 ⊆ 宿主可用集合、Load 校验 guest 导入只属于声明集合（WASI 除外）；内置包与 installed 包统一 `validateRecordSpecs` 校验路径；campus 声明 `ailuo.bus.query` 宿主函数依赖与 `campus/bus` storage 契约（bus 包化步骤 1）。
- **分层重构（2026-08-22）**：公共包契约层 `pkg/packagecontract`（semver、声明、中性清单 `ailuo.package.v2`、lock、进程规格与严格校验）与 `pkg/packmgr` 安装/升级/发布实现分离；Loader 只依赖契约与自身运行时校验，宿主扩展段由安装适配器严格解码为 Registry 规格。
- **阶段 2 核心（2026-08-22）**：Loader 原子升级流程 `Manager.UpgradePackage`——候选组件按依赖拓扑加载、全部健康后**组级原子切换**、旧版本在途全部排空后**反序停止**（消费者先停、Provider 后停）；任一候选失败不切换（旧版原样保留）；Shutdown 有界等待退役组件停止。
- **CLI 与发布流水线（2026-08-22）**：`ailuo install/upgrade/uninstall/list/pack/publish` 落地；`pack` 生成 npm 式 tarball（`<id>-<version>.tgz`），`install` 支持目录/tarball/GitHub Release 源；`publish` 以 GitHub Releases 为分发后端（纯 REST、免 git CLI、版本不可变）；可复用发布 workflow 已在 ci.yml 落地（build → 必填测试 → tag 校验 → pack → tarball 安装冒烟 → artifact → tag 时 publish → 注册表安装闭环验证）。
- **Package/Component 模型（2026-08-23）**：manifest 重构为 `components[]`（Package=分发/版本/升级单位，Component=运行单元，每组件一种 mode）；`packagecontract.ComponentOrder` 按 imports/exports 拓扑排序并拒绝环；lock 按组件记录工件哈希与进程规格；Catalog 按组件产出内核记录（Capability 按 exports 映射到组件运行时，Service/Tools 路由到 Provider 基座）；`Manager.RegisterPackage`/`UpgradePackage` 落地组编排；`hosted`/`isolated` 命名按约定暂不改。
- **消费方 SDK（2026-08-27）**：`pkg/sdkgen` 从 manifest 的 `extensions.capabilities` 严格生成 Go、Python、TypeScript SDK；生成物经编译/导入与真实 HTTP invoke 链路验证，认证和治理 Header 由调用方显式提供。

### 缺口（设计要补齐的）

- **Loader 位于 `internal/`，无法被其他系统直接复用**：需抽取为公共运行时模块，AI珞 内核与中立运行时共用同一份实现（发布 workflow 的 CLI 也因此暂由本仓库构建）。
- **中立运行时不存在**：没有随产品交付的 daemon/可嵌入运行时，也没有宿主能力适配器契约（storage/auth/宿主函数注册面）。
- **注册表服务不存在**：当前以 GitHub Releases 为分发后端（REST、不可变版本），自托管注册表与远端依赖闭包解析待外部消费者出现后落地；依赖解析目前只对本地安装根生效。
- **签名未做**：发布物只有 SHA-256 完整性（manifest/artifact digest 与 tarball 解压校验），无签名。
- **安装目录属主校验仅 Unix**：非 Unix 平台 fail closed（既有 P1）。

## 三、定位：中立基底与宿主

```text
包管理器（中立产品，开箱即用）
├─ 包格式：manifest + lock（语言无关的中性核心）
├─ CLI：init / build / test / publish / install / upgrade / uninstall / list
├─ 注册表协议：REST（npm 风格：发布 / 下载 / 版本索引 / 完整性）
├─ CI workflow 规范：可复用发布流水线
└─ 中立运行时（所有复杂度封装于此，一次实现）
   ├─ 装载、生命周期、沙箱（wazero）、版本解析、lock、drain
   ├─ 无权威状态：实例与 daemon 本身无状态，可复制、可重启
   └─ 宿主能力适配器契约：消费者注册自己的 storage/auth/宿主函数适配器

消费者（不重写装载机制，只接两个小面）
├─ 客户端 SDK：按 capability ID 调用（HTTP `POST /api/v1/capabilities/{capability_id}/invoke`）
├─ 适配器注册：自己的存储/鉴权/身份/宿主函数钩子
├─ AI珞 内核（第一个消费者）：注册 ailuo.store 通用存储、智慧珞珈鉴权等适配器
└─ 未来其他系统：装 SDK + 适配器，开箱即用
```

- **包格式与宿主语义分离**：manifest 中性核心（id、version、language_runtime、abi、entrypoint、artifact、依赖约束、integrity）语言与宿主无关；Tool/Service/Capability、storage、host_functions、权限是 **AI珞 宿主扩展段**，其他宿主可忽略或自行解释。
- **命名保持中立**：工具与格式命名避免品牌绑定（`ailuo` 子命令可更名），不阻碍第三方采用。

## 四、包的定义与形态

### 4.1 Package 与 Component 分离

**Package 是分发、版本与升级单位；Component 是运行单元，每个组件恰好一种运行模式。**
一个包可包含多个组件，通过统一 Capability 通信；只有必须同步发布、升级、回滚的组件
才放进同一个包，能独立演进的应拆成多个包经 Capability 依赖连接。

```jsonc
{
  "schema_version": "ailuo.package.v2",
  "id": "campus.bus",
  "version": "1.2.0",
  "components": [
    { "id": "bus.core", "mode": "hosted", "entrypoint": "bus-core.wasm",
      "exports": ["campus.bus.query"], "imports": ["campus.bus.transport"] },
    { "id": "bus.adapter", "mode": "isolated", "entrypoint": "bus-adapter",
      "exports": ["campus.bus.transport"] }
  ]
}
```

不变量：

1. 一个包可以有多个运行单元，但一个运行单元只能有一种 mode。
2. 组件间通信一律经内核 Dispatcher 路由的 Capability 调用，不直连：wasm 组件调用
   `imports` 中的 Capability 时经宿主函数/内核投影，Host 路由到提供方组件，与提供方
   是 hosted 还是 isolated 无关；提供方在依赖拓扑中先启动、后停止。
3. 全部组件共享包版本；组件版本 = 包版本。
4. 权限按组件分配：wasm 组件不继承 isolated 进程的 OS 权限；数据经 Host Storage
   共享，不共用文件目录。

### 4.2 安装目录形态

```text
<install-root>/<pkg-id>/          # 目录名 = 包 ID（一个包一个目录）
├─ manifest.json                  # 清单（components[] + 包级扩展段）
├─ lock.json                      # 锁定：包版本 + 每组件工件哈希 + 进程规格
└─ <entrypoint>                    # 每个组件的 entrypoint 工件（清单内的 basename）
```

### 4.3 清单结构（中性核心 + 宿主扩展段）

- **包级（中性核心）**：`id`、`version`、`components[]`、`dependencies`（包↔包）、
  `pin`、`idle_ttl_ms`、`storage`（经 Host Storage 共享的数据契约）。
- **组件级**：`id`、`mode`（hosted/isolated，命名暂不改）、`entrypoint`（工件）、
  `exports`（提供的 Capability ID）、`imports`（消费的 Capability ID）、
  `host_functions`（wasm 沙箱权利，第二权限轴）。
- **宿主扩展段 `extensions`**：AI珞 的 `tools`/`service`/`capabilities` 定义
  （包级统一接口，组件 exports 引用其 ID），其他宿主忽略。

```jsonc
{
  "schema_version": "ailuo.package.v2",
  "id": "campus.bus",
  "version": "1.2.0",
  "components": [
    { "id": "bus.core", "mode": "hosted", "entrypoint": "bus-core.wasm",
      "exports": ["campus.bus.query"], "imports": ["campus.bus.transport"],
      "host_functions": [{ "module": "ailuo.store", "name": "list" }] }
  ],
  "storage": { "namespace": "campus/bus", "schema_version": 1,
               "sensitivity": "public", "retention": "permanent" },
  "extensions": { "tools": [...], "service": {...}, "capabilities": [...] }
}
```

### 4.4 双权限轴（不混为一个）

1. **Capability 级 authZ（第一轴）**：每个 Capability 的 `required_permissions`，
   逐调用经 Dispatcher 校验（现有模型，不改）。
2. **沙箱权利（组件级，第二轴）**：wasm 组件的 `host_functions` import 集；
   isolated 组件的 OS 资源限额/进程规格。第二轴只决定"组件在沙箱里能碰到什么"，
   不替代第一轴的逐调用授权——wasm 组件绝不继承 isolated 组件的进程级权利。

### 4.5 运行层抽象（RuntimeDriver）

运行层统一抽象 `RuntimeDriver`（即现有 Loader 的 `Host`/`Runtime` 契约，命名固化）：
`Verify`、`Prepare`（Load）、`Start`、`Health`、`Invoke`、`Stop`。

- **WasmDriver**（hosted）：wazero 主进程内沙箱，启动快、跨平台、默认禁止文件与
  网络访问，适合文本处理、数据转换、普通校园查询等社区包。
- **ProcessDriver**（isolated）：本机 Unix Socket / Named Pipe 上的 gRPC，适合
  Python AI、OCR、浏览器自动化、原生 SDK 等重型能力；仅限官方或可信发布者
  （依赖签名机制，阶段 3 落地前由"安装属受信操作"兜底），并施加 OS 级资源与权限限制。

两种驱动共用统一 Manifest、Capability ID、JSON Schema、权限声明、依赖规则与版本
规范，不形成两套包生态；Agent 与上层业务只调用 Capability，无需感知背后语言或运行方式。

## 五、无状态规范（核心原则）

1. **实例无权威状态**：包实例（Runtime）不保存跨调用权威状态；内存缓存可随时丢弃；实例重启、重建、迁移、升级不丢数据。权威状态一律经 storage 声明落宿主存储（AI珞 按 `app_id` 隔离）。
2. **凭据不落入包**：包不持有数据库凭据、第三方 token、秘密；需要外部能力时经宿主函数投影（受信计算基）。
3. **崩溃语义**：实例崩溃 → 宿主标 `failed` → `RecoverFailed` 重建新实例；在途调用有界失败，已持久化状态不受影响。
4. **幂等与重放**：写类 Tool 必须声明幂等键语义，重放安全（沿用 `internal/kernel/idempotency`）。
5. **存储访问**：业务数据经声明的 storage 端口/宿主函数读写；App 隔离在宿主侧强制（guest 无法伪造 `app_id`）。
6. **禁止项（Verify 与审计拒绝）**：包内自建私有库、包持有第三方凭据、包把用户状态留在进程内、包私建子任务。

验证：实例重启/升级后状态一致测试；崩溃恢复测试；跨 App 隔离测试。

## 六、版本设计

### 6.1 版本号：semver 2.0

- `MAJOR.MINOR.PATCH`（可选 `-pre` / `+build`）。包内全部规格与 runtime 同版本（现有校验已强制）。
- 版本号是包的**公共契约**：对宿主、App 配置、lock、审计均可见。

### 6.2 兼容性语义

| 变更 | 示例 | 行为 | 治理 |
|---|---|---|---|
| patch | 1.0.0 → 1.0.1 | 仅修复；schema、语义、权限不变 | 热替换；无需宿主确认 |
| minor | 1.0.0 → 1.1.0 | 向后兼容新增：新 Tool/Capability、可选参数 | 现有契约不变；**新 Capability 默认不进任何 App**，需宿主控制面显式启用 |
| major | 1.x → 2.0.0 | 破坏性：schema、语义、权限、存储 schema 变更 | 宿主控制面显式确认（generation CAS）；可能伴随存储迁移 |

### 6.3 版本约束与解析

- 约束语法：精确 `1.2.3`；caret `^1.2.0`（≥1.2.0 且 <2.0.0）；范围 `>=1.0.0,<2.0.0`。
- 解析时机：安装/升级时按约束解析被装包自身的版本 → 写入 lock（固定版本 + 每组件工件 SHA-256）。`dependencies` 在安装时对**已安装集合**逐条校验（缺失或不满足约束即 fail closed），但**不做闭包求解、不自动拉取传递依赖**，lock 也不记录闭包（见 §九 打包行）。
- **版本唯一性**：同一宿主内同一 `tool_id` / `capability_id` 只允许一个已发布版本；升级是版本替换，不做多版本并行（避免路由歧义；有明确需求再放宽）。
- 冲突：依赖在已安装集合中不可满足 → fail closed，须先装齐依赖或显式调整约束。

### 6.4 升级与降级（以 Package 为单位）

升级以整个包为单位，组件作为组编排：

1. 校验全部组件清单与权限（第一轴 + 第二轴）；
2. 按依赖拓扑启动候选组件（通常先启动 isolated Provider，再启动依赖它的 wasm 组件）；
3. 全部组件健康后，**原子切换整个包**（切换只是指针替换，无部分失败）；
4. 旧版本按依赖反序 drain（`in_flight` 归零后，消费者先停、Provider 后停）；
5. 任一候选组件失败 → **不切换**（旧版本原样保留，可回滚）；切换后的运行时故障是
   显式降级操作，不是升级的一部分。

- **minor/patch 升级**：候选组全绿后原子切换；宿主配置与 Run 状态不受影响。
- **major 升级**：宿主控制面显式确认；存储迁移前向执行成功后激活；失败保留旧版本。
- **降级**：仅工件/代码回滚到 lock 上一版本；存储 schema 只前向，不自动回滚数据。
- **升级不扩权**：新增 permissions 不自动进入既有 App（鉴权设计 6.2）。
- 升级全程幂等；失败保留旧句柄供 Shutdown 清理。

## 七、多语言支撑

| 运行模式 | 语言 | ABI | 现状 |
|---|---|---|---|
| hosted | 可编译 wasm32-wasi：Rust、Go(tinygo)、C、AssemblyScript 等 | stdin/stdout JSON 信封 + 宿主函数 import | wazero 沙箱已实现；测试使用通用 WASM 固件 |
| isolated | 任意语言（Python/Go/Rust/...） | `runtime_host.proto` gRPC unary | 协议、监管、进程规格已实现 |
| embedded | 宿主内嵌语言（Go） | 进程内函数 | 机制已有，无生产包 |

- **per-language SDK（新增，主要投入）**：`ailuo-sdk-go` / `ailuo-sdk-rust` / `ailuo-sdk-python` / `ailuo-sdk-ts`，提供统一 Host API（`ctx.storage`、`ctx.http`、`ctx.identity` 等）与信封编解码、schema 助手、生命周期骨架——作者只实现 Capability，不直接处理 WASM 内存或 gRPC 生命周期；SDK 与 CLI 共享同一契约定义，避免各语言漂移。V1 用 JSON Schema 描述接口、Protobuf 管理控制面、JSON 信封承载调用；未来 WIT 工具链成熟后再迁移强类型接口。
- **`ctx.http` 是 SSRF 高危能力**：wasm 沙箱默认无网络，`ctx.http` 由内核代包发请求，必须限定目标（域名 allowlist、拒绝内网 IP、超时/重试/审计）；`ctx.storage` 相对安全（宿主侧隔离强制）。
- **能力差异**：wasm 无文件系统/网络（WASI 裁剪）→ 需要内核能力必须走宿主函数；isolated 进程可自行访问网络，但凭据仍经宿主投影（fail closed）。
- 契约中立性：SDK、信封、gRPC 定义均不引用 AI珞 业务语义，其他宿主可复用。

## 八、宿主函数投影（host function）

- 宿主维护**宿主函数注册表**：`module.name → 实现`（AI珞 内核 Go 代码，受信计算基）。当前实例是通用 `ailuo.store`（get/list/put/delete：namespace 绑定包声明、App 隔离宿主强制、快照元数据内嵌单事务一致读）；按包定制的宿主函数已随 `pkg/bus` 移除，新增有状态包零内核改动。
- 包 manifest 声明所需宿主函数；**Verify 时**校验注册表包含；**Load 时**只投影声明集合（wasm 侧只 import 声明的 module/name，未声明调用直接拒绝）。
- 内置包与安装包共用同一注册表与投影校验。
- 通用宿主函数能力面（`storage.*`、`observe.*`、`identity.*` 等）作为逐步投影候选，每个都有闭式协议、App 隔离强制与泄露负向测试。
- **中立性**：宿主函数是 AI珞 宿主能力，不是包格式的一部分；不依赖它们的包（无 host_functions 声明）可在任何宿主/独立环境运行。

## 九、CI workflow 规范（npm 式发布流水线）

包作者仓库的标准发布流水线，以**可复用 workflow**（GitHub Actions `ailuo-package-publish` 等）形式提供，各包仓库 `uses:` 即得：

| 阶段 | 内容 | 产出/校验 |
|---|---|---|
| 构建 | 按 `language_runtime` 构建（wasm 交叉编译 / 原生构建）；固定工具链版本保证可复现 | 可复现工件 |
| 测试 | 单元测试 + 对宿主 substrate 的集成测试（wasm 信封 golden、gRPC 契约） | 测试证据 |
| 版本 | semver 由 conventional commits 或显式 tag 决定；校验 `manifest.version` 与 git tag 一致 | 版本一致 |
| 打包 | 生成 manifest + lock + artifacts + integrity（SHA-256）；lock 目前只固定每组件工件哈希，依赖解析闭包待补 | 完整安装目录 |
| 发布 | 推送注册表（注册表鉴权只认证包作者，**与智慧珞珈无关**）；SLSA provenance；签名（预留） | 不可变版本 |
| 安全 | 依赖漏洞扫描、secret 扫描、工件哈希复核 | 通过门禁 |

- 可复用 workflow 的 `test-command` 是必填发布前门禁；`package` job 输出已验证发布物的 `artifact-id`，发布 job 只下载该 artifact，不执行调用方构建命令。
- **不可变版本**（npm 式）：注册表已发布版本不可覆盖；错误版本通过新版本修复。
- 发布是受信操作（CI 角色/控制面），与运行期调用鉴权无关。
- 门禁：包作者 PR 必须通过 CI 才能发布；发布事件全审计（包 ID、版本、发布者、结果）。

## 十、鉴权独立性

### 10.1 两个鉴权面（均服务端统一）

| 鉴权面 | 作用 | 归属 |
|---|---|---|
| 注册表鉴权 | 包发布者/下载者身份认证（npm 式），与智慧珞珈无关 | 注册表服务端统一处理 |
| 运行时鉴权 | 每次调用的身份解析 + 授权校验 | 经宿主能力适配器契约在服务端统一执行；AI珞 三层鉴权是参考实现，其他系统通过同一适配器接口接入自己的策略引擎 |

- 接口统一、策略归消费者：适配器契约（身份解析、授权检查、审计回调）由中立运行时定义；AI珞 的 `鉴权与委托授权设计.md` 三层模型是其实现之一，不是唯一实现。
- 包管理器不实现具体鉴权策略；具体策略永远在服务端（消费者/宿主侧），客户端与包不可绕过。

### 10.2 智慧珞珈范围

- 只有涉及智慧珞珈数据/身份/委托 token 的包，在 manifest 声明对应宿主函数（如未来 `ailuo.luojia.*`）与权限需求 → AI珞 宿主按 `鉴权与委托授权设计.md` 三层模型强制执行。
- **其他包完全独立**：工具类、公开数据、纯计算包不声明任何鉴权需求，可在任何宿主/独立环境运行；智慧珞珈的接口、SSO、委托 token 对它们不存在。
- 边界：声明 `ailuo.luojia.*` 宿主函数的包只能运行在提供该能力面的 AI珞 宿主；未声明的包与宿主无关。
- 数据接入模式 A（机构授权）/模式 B（用户委托）只作用于智慧珞珈数据包，不扩散到整个包生态。

## 十一、bus 包化（第一个验收）

### 11.1 现状

`campus` 是经独立包仓库发布、由安装目录装载的 hosted 包：guest 自包含（只依赖标准库），经通用 `ailuo.store` 宿主函数读写宿主统一存储；数据权威元数据与文档存储由内核 `internal/kernel/packstore` 窄端口 + SQLite/内存实现承载；demo 播种经同一端口。安装清单由 `ailuo pack` 从作者侧 `ailuo.toml` 生成。

### 11.2 目标形态（两步）

**步骤 1：契约统一（不改变内嵌形态）**

- manifest 增加 `storage`（`campus/bus`、schema_version）与 `host_functions`（`ailuo.bus.query`）声明；
- 宿主函数注册表 + 按包投影校验接入 campus（内置/安装同路径）；
- 依赖约束化：`ToolDependencies` 升级为带版本约束。

**步骤 2：真正安装（安装目录包）**   ✅ 已完成

- `campus.bus` 工件 + manifest + lock 由工具链生成（`ailuo pack` 经 `[build]` 自动编译）并放入安装目录（`AILUO_RUNTIME_INSTALL_ROOT` 显式指定，缺省为用户配置目录 `ailuo/runtime`——`ailuo install` 与内核启动共享同一默认位置，无需 `--root`）；内核启动发现、校验、注册、装载与任何安装包一致（安装目录 hosted 包声明 host_functions 时由进程内 WasmHost 装载，宿主函数是内核特权，跨进程无法投影）。
- `pkg/bus` 中立包（2026-08-24 引入，**2026-08-30 移除**）：guest 自包含化后该包失去存在意义。guest 只 import 标准库，领域模型与治理逻辑全部在包仓库内；内核侧持久化统一走 `internal/kernel/packstore` 端口（`ailuo.store` 宿主函数背后）。
- 内置 `campus.Record()`/`campus.Host(store)` 生产路径移除：campus 不再内置，所有环境从安装目录装载；启动时缺失 campus.bus 拒绝就绪（fail-closed）。Core 测试只使用通用运行时固件，不维护无业务价值的示例 Package。
- 安装目录属主校验仅 Unix 支持（非 Unix fail-closed，既有 P1）。
- demo 数据作为**开发环境种子**（非权威、显式标记、生产禁启用）；生产数据仍经授权 ingestion 写入统一存储；卸载/升级不丢存储数据（存储归宿主，包只声明不持有）。

### 11.3 边界

- guest 业务逻辑自包含在包仓库（只依赖标准库，不依赖内核 `internal/` 与 Core 仓库任何包）；持久化经通用 `ailuo.store` 宿主函数，作用域强制为（App × 包 namespace），数据新鲜度/权威性治理在 guest（读取响应内嵌单事务一致的快照元数据）。宿主把包错误转换为通用 Runtime Invocation 错误，Core 不识别包的领域错误类型。
- 新增**有状态包零内核改动**：包声明 `[storage]` namespace 与 `ailuo.store` 函数子集即可持久化；快照原子替换（`ReplaceSnapshot`）仅对可信 Go 侧开放，供未来授权 ingestion（学校 API OAuth 后写入）使用。
- 校车、校历等后续校园包复用同一包化路径，各自独立安装/升级。

## 十二、权限、治理与可观测性

- **安装 ≠ 授权**：包注册进宿主 Registry 不等于任何 App 可用；App 显式启用并收窄 permissions（鉴权设计六，不改）。
- **控制面/CI 专属**：安装、升级、卸载、发布属于受信控制面（9178 loopback admin + 运维 CLI + 发布 CI），普通用户与 Agent 不可触发；操作全审计。
- **签名预留**：当前保持 SHA-256 锁定；manifest 预留 `signature` 字段，密钥分发方案落地后启用（先哈希后签名，不破坏既有安装目录）。
- **可观测性**：沿用现有 Loader metrics（load/stop/调用数/耗时）；补包版本、升级事件、拒绝投影等低基数标签；包正文、参数、结果不进普通日志（现有净化规则）。

## 十四、作者零声明（源码契约自动生成）

### 14.1 设计原则

- 纯计算包**零声明**：作者只写 guest 源码与 WASI stdin/stdout 信封入口，`ailuo pack --version <semver>` 自动提取清单（component/build/capability）并构建；版本不由生成器永久固定。
- 提取器按语言分离，统一输出 **JSON Schema**（语言中立桥接）：Go 用标准库 `go/ast` 静态分析（wasip1 交叉编译无法运行时反射，故不引入反射式 schema 库）；TypeScript 用固定版本 `ts-json-schema-generator@2.4.0`。
- 需要宿主函数/存储的包仍用最小 `ailuo.toml` 声明（机器无法推导的内核特权），tool/schema/capability 仍自动生成——无双轨。

### 14.2 Go 提取约定（`schemaextract.AnalyzeGo`）

```go
// hello 说你好。                          ← 注释首行 = capability 描述
func hello(args HelloArgs) (json.RawMessage, error) { ... }

type HelloArgs struct {
    Name string `json:"name"`             // 无 omitempty → required
    Count int   `json:"count,omitempty"`  // omitempty → 可选
    At    time.Time `json:"at,omitempty"` // time.Time → format: date-time
}
```

- 包级小写函数 = capability（`包ID.函数名`）；参数 struct 的 json tag 与字段类型派生 JSON Schema。
- 字段映射：`string/int64/float64/bool` → 对应标量；`time.Time` → date-time；`[]T`/嵌套 struct → array/object；未知类型、无 tag 字段 fail-closed。
- object 统一 `additionalProperties:false`（与内核严格解码一致）。

### 14.3 TypeScript 提取约定（`schemaextract.AnalyzeTS`）

```ts
// hello 说你好。
export function hello(args: HelloArgs): any { ... }
export interface HelloArgs {
  name: string;
  count?: number;
}
```

- `export function <小写名>` = capability；参数类型名约定 `<CapabilityName>Args`（首字母大写）。
- schema 由 `npx --yes --package ts-json-schema-generator@2.4.0 ts-json-schema-generator` 从类型生成（`--no-top-ref`），不手写 TS 解析器；消费方生成 SDK 时由 `sdkgen` 校验其严格子集。

### 14.4 构建器

| 构建器 | 源码 | 命令 | 前提 |
|--------|------|------|------|
| `go-wasm` | `main.go` | `go build -trimpath -o main.wasm .`（GOOS=wasip1） | Go 工具链（门禁既有前提） |
| `ts-as` | `main.ts`（AssemblyScript 语法） | `npx --yes --package assemblyscript@0.27.31 asc main.ts -o main.wasm` | node/npx |

- hosted 调用契约为 WASI stdin 信封 + stdout 结果信封 + `_start` 入口（WasmHost 强制）；自动提取只生成契约，不生成函数分发器，guest 必须自行实现该入口（Go 经标准库，AssemblyScript 需 WASI 适配）。

### 14.5 生成流程

```text
main.go / main.ts
  → schemaextract（按语言提取器）→ Capability{ID, Description, InputSchema}
  → ManifestFromCapabilities（component/build/capability 自动推导，extensions 复用继承规则）
  → [build] 构建 → 打包 → 安装 → 生成 SDK
```

## 十五、消费方 SDK（契约生成）

### 15.1 设计原则

- 从包清单的 `extensions` 段（tools/service/capabilities + JSON Schema）**自动生成**各语言 SDK，不保留手写 SDK 或兼容回退。
- 生成的 SDK 仅用标准库，不依赖内核 `internal/` 包，可被外部项目直接 `go get` 复用。
- 一个生成入口（`pkg/sdkgen.Generate`），跨语言 emitter（Go + Python + TypeScript）。

### 15.2 类型派生规则

| JSON Schema | Go | Python | TypeScript |
|-------------|----|--------|------------|
| `string` | `string` | `str` | `string` |
| `integer` | `int64` | `int` | `number` |
| `number` | `float64` | `float` | `number` |
| `boolean` | `bool` | `bool` | `boolean` |
| `string` + `format:date-time` | `time.Time` | `datetime` | `Date` |
| `string` + `enum` | 具名 type + const | class(str, Enum) | string literal union |
| `array` + `items` | `[]T` | `list[T]` | `T[]` |
| `object` + `properties` + `additionalProperties:false` | 具名 struct | `@dataclass` | `interface` |

非必填标量与对象字段 → 指针（`*T`/`Optional[T]`）；Go 非必填数组 → `*[]T`，区分未提供与显式空数组；Python/TypeScript 分别使用 `Optional[list[T]]` 与可选属性。
非必填标量与对象字段 → 指针（`*T`/`Optional[T]`/属性级 `?`）；Go 非必填数组 → `*[]T`，区分未提供与显式空数组；整数 `enum` 在生成前即被拒绝（`KindEnum` 只承载字符串）。

### 15.3 传输层信封

- 端点：`POST /api/v1/capabilities/{capability_id}/invoke`
- 请求：`{"input": <payload>}`（严格解码，禁止未知字段 / 尾随内容）
- 响应：`{"capability_id": "...", "result": <value>}`
- 治理（App 策略、权限收窄、Schema 校验、幂等/确认）由内核 Dispatcher 统一执行，HTTP 层只做信封与鉴权。
- 认证：生成客户端提供调用方 Header/认证材料注入点；认证失败不会降级为匿名身份。
- 治理 Header：副作用调用使用 `Idempotency-Key`，已批准确认使用 `X-Confirmation-ID`；两者由调用方显式传入。
- 稳定错误映射：`400 invalid_input`/`invalid_idempotency_key`、`401 authentication_required`、`403 permission_denied`、`404 capability_not_found`、`409 idempotency_conflict`/`confirmation_required`、`503` 受治理数据状态、`504 deadline_exceeded` 等（不泄露内部细节）。

### 15.4 现在与未来

- 已实现 emitter：Go（方法 + 类型化 struct）、Python（函数 + 类型化 dataclass）、TypeScript（`Client` class + `interface`，async/await + fetch），均经可编译/导入验证（Go `go build`、Python `compileall`、TypeScript `tsc --strict`）。
- 契约模型独立于内核 internal 包，第三方可 `go get github.com/projectluojia/AI-Luo-Man-ga/pkg/sdkgen` 定制 SDK 生成。
- WIT 工具链迁移（本设计文档所述未来项）从 `pkg/sdkgen` 的 JSON Schema 派生模型演进，不推翻当前契约。

## 十六、实施路线

1. **阶段 1（契约与投影）**：manifest 中性化（核心 + 宿主扩展段）；宿主函数注册表与按包投影校验；内置/安装包统一校验路径；bus 包化步骤 1。
2. **阶段 2（版本与生命周期）**：semver 约束解析器与 lock 生成；升级/降级流程（原子切换 + drain）；major 升级的宿主确认与存储迁移挂钩；`ailuo` CLI 基础（install/upgrade/uninstall/list）。
3. **阶段 3（发布与 CI）**：CI workflow 规范与可复用发布流水线；`ailuo publish`；注册表协议 v1（REST）；签名。
4. **阶段 4（生态）**：扩展 per-language SDK（当前已实现 Go/Python/TypeScript 生成器）；更多通用宿主函数能力面；注册表服务与外部宿主接入。

## 十七、验收清单

- 无状态：实例重启/升级/崩溃恢复后权威状态一致；包内建库、持凭据、留用户状态被 Verify/审计拒绝。
- 版本：semver 约束解析正确；lock 固定可复现；冲突 fail closed；升级原子切换；降级不回滚数据。
- 投影：包声明外调用宿主函数被拒绝；内置/安装包同校验路径。

- CI：包作者仓库接入可复用流水线后可完成构建→测试→版本→发布；不可变版本；发布审计。

- bus 包化：`campus.bus` 可安装/升级/卸载；卸载不丢存储数据；demo 种子生产禁启用。
- 治理：安装 ≠ 授权；升级不扩权；控制面/CI 操作全审计；签名预留不破坏既有目录。
