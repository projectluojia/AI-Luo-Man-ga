# AI珞（爱珞）系统架构说明（实现基线）

> 状态：按 2026-09-01 仓库代码整理的**实现基线说明**。
> 本文是当前架构、装配流程、数据流和 fail-closed 边界的唯一主说明；设计、路线和专项契约分别见同目录的路线图与专项文档。

## 一、系统定位与分层

AI珞（爱珞）是一个多入口执行平台：**Go 内核是唯一核心与事实权威**，具体 Executor 只承担一次受治理的执行闭环，业务能力以 Service/Tool 装配在能力面。当前仓库包含 Python Agent Executor 与校园包化纵向切片。

逻辑三层（与部署正交，不一一对应进程）：

| 层 | 内容 | 权威性 |
|---|---|---|
| L1 托管持久化 | SQLite（统一数据库）+ Blob 文件存储 | 有状态，权威数据只落在这里；连接与凭据只由 Go 持有 |
| L2 Go 内核 | 接入、Echo/Run 编排、鉴权、注册表、路由、队列调度、Loader、可观测性、审计 | 系统治理与编排，无业务故事 |
| L3 能力面 | 安装包 Runtime + `internal/kernel/packstore`（包持久化窄端口，`ailuo.store` 宿主函数） | 无本地权威状态，经 Dispatcher 调用，数据经存储端口回写 L1 |

前端与外部平台（Web、QQ、未来渠道）只连接 Go。Executor 与扩展包是受治理的执行者/能力提供者，不直接访问 Core 数据库、外部平台或后台任务。

```text
Web / QQ / 未来平台
      │  适配器规范化
      ▼
Go 内核：Hub.Intake（校验→身份→会话/消息入库）
      ▼
Echo 创建（幂等）→ 持久队列 → 内核调度器（`echo.Scheduler`）
      ▼
Orchestrator → 执行者协议（executor.proto，双向流）→ 任意 Executor Runtime（当前生产包为 Python Agent）
      ▼
Capability 调用（Dispatcher：Schema/权限/深度/取消/幂等/确认）
      ▼
Loader 租约 → hosted/isolated 运行时
      ▼
      已安装 Service / Tool Runtime → `ailuo.store` 端口 → SQLite
      ▼
SSE / 平台回发
```

## 三、核心流程

### 3.1 消息入站与标准化（Hub.Intake）

所有渠道的原始事件先由适配器规范化为标准 `InboundMessage`，再经 `access.Hub.Intake` 走受治理链路：

1. **校验**：App 匹配、platform/platform_message_id/幂等键必填、文本 ≤4000 字符、附件数量上限。
2. **身份解析**：所有用户消息都必须携带 `PlatformUserID`，经 `identity.Service.ResolveIdentity` 解析为内部 `user_id` 与有效 AppMembership（缺失 → 401 `authentication_required`，未绑定 → 401 `identity_not_found`，禁用或非成员 → 403）；不存在匿名发送者或匿名会话降级。
3. **会话找到或创建**：按版本化规范结构生成 `session-v1-<sha256>`。direct 键覆盖 App、平台、渠道、平台空间、平台会话和内部用户；group 键覆盖前五项但不含单个发送者。SQLite 在同一事务内校验会话类型/平台绑定并幂等补写群成员。
4. **消息持久化**：以幂等键为 message_id 写入消息库；重复投递（相同 app_id+platform_message_id）返回既有消息且 `Created=false`。

上层（Web/QQ/ingress）在 Intake 成功后以**同一幂等键**创建 Echo：消息与 Echo 两侧共享去重，重放不产生重复消息、不产生重复 Echo、不重复回复。

平台适配器（Web 表单、QQ OneBot、ingress 事件）都不直接创建 Echo、不写消息库、不解析身份——这三个动作全部收敛在 Hub 与上层编排里。

### 3.2 Echo/Run 生命周期与调度

- **创建**：`Orchestrator.CreateEchoRunIdempotentLimited` 原子完成"Echo 终态表 + 持久 Run 排队"，`app_id+echo_id+attempt` 唯一约束，重复客户端请求安全重放。
- **调度**：持久 Run 队列由 `internal/kernel/echo.Scheduler` 消费，固定 4 worker、250ms 轮询、App 容量上限 128；main 统一负责恢复与关闭，Web、QQ、ingress 只在创建成功后发送低延迟入队通知，重启仍从 SQLite 恢复。
- **执行**：worker 取到 `RunWork` 后调用 `Orchestrator.RunQueued`：校验持久 Run → 固化配置修订 → contextasm 装配中性 Context Block → 与 RoleExecutor 建立双向流 → 执行者自行解释输入/上下文/opaque 配置。
- **重试与恢复**：Run 有 3 次 attempt；仅"无副作用前"的稳定错误按持久 `available_at` 延迟重试；活动 Run 的 lease 周期续期；启动时 `Recover` 按策略确定性处理遗留 `running` 记录（恢复/重试/取消/失败）。
- **事件**：`echo.started / run.context / run.started / capability.completed / output.delta / run.completed / run.failed` 持久化（序列单调，跨 attempt 不冲突），SSE 支持 `Last-Event-ID` 重放；Executor 内部是否递归由包自行处理，Core 只发布当前普通 Run 事件。

### 3.3 执行者协议（executor.proto）

- 内核与任意 Executor 协商协议版本，双向帧序列：`StartRun → (ExecutorFrame)* → 终态`；严格校验未知帧、重复/迟到结果、越界载荷、未知事件类型。
- `StartRun` 只携带治理所需的输入/上下文 payload、Capability 投影、通用执行单元预算和追踪/因果标识；不包含模型、Provider、系统提示或其它具体执行者配置字段。
- 当前 Python 包在自己的运行时内把上下文 payload 解释为模型上下文，并从自身 Deployment 配置读取模型/Provider；其它执行者可以使用不同的 payload 解释，不需要修改 Core。
- Provider 调用的超时、取消传播、限流和重试属于具体执行者包；Core 只校验执行者上报的通用用量与协议边界。

### 3.4 Capability 调用链（Dispatcher）

`InvokeCapability`/`UseTool` 两条路径走同一治理序列：**校验 → 当前策略快照 → Registry 解析 → 权限授权与收窄 → 严格 Schema 重验（Go 侧，不信任 Provider strict 模式）→ 子请求上下文（深度+1、调用链追加）→ 幂等 → 确认验证（未批准 fail-closed）→ 执行 → 审计**。

- 权限与数据范围只允许收窄；内部调用不获得额外信任。
- 调用深度上限（默认 16）与不前进循环检测在 Dispatcher 强制。
- `ToolID` 注入治理上下文，运行时级 Handler（含 hosted guest）据此分发；guest 无法伪造 app_id/权限/调用链（宿主函数投影按调用上下文绑定）。
- 每次 Capability 调用写审计（App 隔离、脱敏）；审计写失败把成功结果翻转内部错误（fail-closed）。

### 3.5 Loader 与运行模式

- **统一 Manager**：一个 Loader 持有全部模式宿主（安装目录包的进程内 WasmHost、通用 ProcessHost、installed 的 GRPCHost 同池）。清单注册时按 `Verify` 精确绑定唯一宿主（零/歧义匹配在注册期 fail-closed），绑定固化在条目上。
- **角色**：`capability`（能力提供者，实现 Invoker）/ `executor`（执行者，实现 `executor.ClientProvider`）。角色是运行时身份的一部分，升级不允许改变。Deployment 可安装多个执行者，`Manager.Executor` 按 App 的 `ExecutorID` 精确选择，ID 缺失或角色不符时 fail-closed。
- **两种运行模式**：
  - `hosted`：wazero 沙箱执行 wasm32-wasi 工件；线性内存上限（默认 128 MiB）、WASI 裁剪（无文件系统/网络/环境变量）、每次调用独立实例、执行时间预算（默认 30s，预算耗尽按 DeadlineExceeded 归类强制终止，无"不限时"路径）、stdin/stdout JSON 信封 ABI。
  - `isolated`：独立进程监督，复用 loader 进程原语（StartProcess/Reap/Terminate/Kill/Release）；进程启动模板由包作者显式声明，安装器自动解析并锁定，Loader 不根据 entrypoint 猜测命令；Linux `prlimit`、Windows Job Object（KILL_ON_JOB_CLOSE 防孤儿）强制资源限额；非零限额在不支持的平台 fail-closed。
- **安装目录**：`manifest.json`+`lock.json` 严格 JSON/digest 校验、属主校验（Unix UID / Windows ACL SID）、工件哈希防 TOCTOU 替换；Core 只装载项目 `ailuo.lock` 列出的包，锁缺失、清单摘要/版本/安装 lock 摘要漂移时 fail closed；isolated 组件必须由清单显式提供进程模板；安装目录配置了 hosted 包而宿主地址缺失时内核拒绝就绪。
- **外部 Runtime Host**（`runtime-host --project-root` 子命令）：独立进程只承载项目 `ailuo.lock` 中列出的 installed hosted 包（无宿主函数声明的）。协议身份携带 ID/Version/Mode，`catalog.ReadArtifact` 按身份比对（2026-08-14 修复：此前全清单比较导致真实接线必然失败）；`runtime_host_wiring_test.go`（`//go:build unix`）用真实安装目录 + 真实 Backend 覆盖 GRPCHost → 协议 → wazero 全链路。host function 是内核特权：声明宿主函数投影的工件（campus.bus）只能内核进程内 WasmHost 执行，GRPCHost 拒绝跨进程投影（fail-closed）。

### 3.6 存储层

- 单一 `sqlite.Store`（单连接、多文件分域）实现全部域端口（echo/session/identity/appconfig/confirmation/idempotency/task/context/metrics）；域代码只依赖窄端口。
- 迁移注册表机制：`registerMigration(version, sql)` 多模块独立注册前向迁移，当前 Schema 1–27 连续；已应用迁移不可改写。旧模型/提示词列只出现在历史迁移和备份校验中，当前 Store 不查询。
- App 隔离贯穿所有表：复合主键与索引含 `app_id`；参数化 SQL；动态标识仅来自代码内白名单。
- 备份/校验/恢复为独立命令（`backup`/`validate-backup`/`restore`），SQLite 一致性备份 + 完整性/外键/schema 校验 + 无覆盖离线恢复。
- 迁移 21 为保留 `app_config_heads` 的非破坏性 no-op（2026-08-14 修复：原为清空当前配置指针的破坏性迁移，升级会丢弃控制面调优的当前配置）。
- 迁移 22 保存 App-scoped QQ Access 当前配置（OneBot 地址、机器人 QQ 号、群/私聊白名单和 generation）；NapCat 保持独立。9178 控制面保存 Deployment 配置后重启内核，QQ Manager 启动时通过 CAS 应用当前修订，实际准入仍完全位于 QQ Access。
- 迁移 23 是旧版本用户提示词偏好表的历史步骤；当前内核不再提供 Prompt Service，旧表仅为保持数据库升级链连续而保留。
- 迁移 24 是历史 Run 输入列的前向兼容步骤；当前输入统一从 `input_payload` 读取，不再提供嵌套 Run 语义。
- 迁移 26 将 App/Run 的模型、Provider 和提示词字段转换为 `ExecutorID` 与 opaque `ExecutorConfig`；迁移 27 归一化旧 `agent_*` 错误分类。

### 3.7 身份 / 会话 / 后台任务

- **身份**：Deployment 级 User + App 级 ExternalIdentity/AppMembership/IdentityBindingRevision（roles/permission_grants 表保留为 Schema 契约）；外部平台 ID 永不充当内部 user_id；同一外部身份并发绑定由库唯一约束互斥；禁用查询时实时生效。控制面入口只有 CreateUser/BindExternalIdentity/UnbindExternalIdentity/ResolveIdentity/SetMembership/DisableUser（`identity-bind`/`identity-unbind` 命令 + Hub 解析），2026-08-14 清理删除了无生产调用者的角色/权限授予管理面（14 个 Service 方法 + 8 个存储方法 + `--roles` 旗标）。
- **会话/消息**：Session（direct/group/system）+ Message（content_ref、回复、编辑、软删除）；Blob 存储只存正文引用（沙箱负向测试保留，写入原语待附件接入落地）；`session.Service` 只保留读路径（ListMessages/MessageContent 供 contextasm 装配），消息写入由 Hub 直写 Store；消息正文不进日志与审计。
- **后台任务**：持久 Task 状态机（租约领取/续期/死亡恢复/有界重试/App 容量隔离/封闭类型注册表+参数 Schema 双重校验）；首个消费者为确认过期清扫（`governance.confirmation.expiry`，5 分钟周期，任务自续链，启动播种一轮）。

### 3.8 可观测性

- 统一 `internal/observe`（Go）与 `agent.observe`（Python）：中文结构化日志，控制台/JSON 双格式，字段键英文稳定。
- W3C `traceparent` 从 HTTP 贯穿 Go Run 与外部 Executor span。
- Prometheus 指标：HTTP、Runs/队列、首 Token、Provider 重试、usage/成本、Capability、Tool、存储。
- 审计独立于普通日志：集中脱敏、App 隔离、保留策略；凭据、消息正文、Tool 参数、Provider 原始响应永不进入日志/审计/公共 API。

## 四、信任边界与 fail-closed 语义

以下边界**拒绝失败（fail-closed）**，不存在静默降级：

- 未完成本机配置、未能为当前 App 唯一解析 Executor 或 Executor 未就绪：9178 本机配置控制台保持运行，业务内核不进入就绪；Executor 专属凭据和配置由其包自己的 Deployment/监督器管理，Core 只保存 Executor ID 与 opaque 配置。当前 Agent 默认由外部 Deployment 启动，Core 只连接；Core 托管启动不继承自身环境。
- 安装目录配置 hosted 包但宿主地址缺失：拒绝就绪（无进程内回退）。
- 执行者解析：按 App 配置的 `ExecutorID` 选择安装锁中的 `role=executor` 组件；ID 缺失、未锁定或角色不符 → 装配期 fail-closed。
- Dispatcher：未批准确认、Schema 不符、权限不足、深度超限 → 拒绝执行；审计写失败 → 结果翻转内部错误。
- Executor：未投影 ToolCall、畸形/重复/迟到帧、超预算 → 拒绝/终止；版本协商不兼容 → 拒绝。
- hosted：预算耗尽强制终止；未知 guest 错误码视为协议违例；WASI 无文件/网络/环境。
- 进程限额：非零限额在无原生支持的平台拒绝启动（Windows max_open_files/max_file_bytes 同理）。
- 数据治理：过期/不完整/非权威快照不返回业务行；guest 的领域错误在 Runtime 边界转换为公共 `data_expired`/`data_incomplete`/`data_non_authoritative` 等稳定错误码；Core 不内置或播种业务演示数据。
- 身份：身份缺失或 Web 未配置可信认证器 → 401；平台身份未绑定 → 401；用户禁用或没有 AppMembership → 403；Hub 缺少身份解析器时拒绝构造。

**有意为之的宽松路径**（设计文档化，非缺陷）：

- QQ 适配器断线重连（5 秒退避），适配器失败不影响内核就绪——平台适配器与内核解耦是文档契约。
- 没有合法的 W3C traceparent 或 X-Trace-ID 时生成新的 trace 根，不用 echo_id 冒充 trace ID。
- 慢消费者从 EventHub 驱逐（驱逐后无信号，消费方按"流结束"处理；QQ 侧静默不回发是已知边界）。
- Web 登录态解析器尚未接入主程序，因此 Web 聊天创建入口当前 fail closed 返回 401；健康检查、状态读取等非聊天入口保持可用。
