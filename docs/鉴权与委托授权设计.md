# AI珞 V3 鉴权与委托授权

> 状态：与 Package/Component/Capability 统一模型对齐。身份认证、数据源凭据和
> Capability 授权仍是三个不同边界。

## 一、三类边界

1. 身份认证回答“调用者是谁”：由 Go Access、Identity 和 AppMembership 解析；外部
   平台用户 ID 不能直接作为内部 user_id。
2. 数据源鉴权回答“能否访问学校系统”：凭据由受信 Provider/Deployment 管理，不能
   进入普通日志、Executor 或公共 API。
3. Capability 授权回答“本次能做什么”：由 App allowlist、权限范围、Run scope 和
   Dispatcher 在每次调用时共同决定。

三者不能互相替代。机器能连接平台，不代表某个用户有权限；Package 声明所需权限，
也不代表任何 App 已授权。

## 二、Capability 授权规则

- 安装、注册和授权是三个独立动作。
- App 对 Capability 默认拒绝；受信控制面使用 generation CAS 显式启用和授予权限。
- Package 升级不得自动扩大既有 App 的 Capability Grant、资源范围或预算。
- Dispatcher 在 Go 边界再次校验 Capability ID、Schema、权限交集、deadline、幂等键
  和确认记录；Provider/Executor 提供的 strict 模式不是安全边界。
- 内部 Capability 调用只能收窄权限，不能借调用链获得额外权限。
- write/external Capability 需要持久幂等键；结果未知时进入人工/对账路径，不自动重做。

## 三、委托与 child Run

Executor 不能在进程内私建子执行。root Run 调用 `run.create_child` 时，Core 校验：

- 父 Run 属于当前 App、处于可创建状态且仍有租约；
- child Capability 集合同时属于父 Run 上界和当前 App allowlist；
- child 所需权限属于父 Run 与当前策略的交集；
- deadline、步数、Capability 调用数、Token、输出和成本预算均有独立上限；
- child 只能是 root 的直接子节点，不能再次派生。

Core 原子持久化 child 的 `parent_run_id`、来源 `call_id`、scope、预算、租约和 queued
状态，调度器随后按普通 Run 规则执行。结果只通过持久状态和受治理事件返回给父 Run。

## 四、数据源委托

需要学校系统数据的 Provider 通过显式 Capability 取数。它只返回受约束的数据结果，
不直接写业务数据库；Core 校验来源修订、权威性、完整性和有效期后，再原子写入 App
隔离的 Storage namespace。任何过期、非权威或不完整数据都返回稳定错误，不由模型猜测。

OAuth/token 的绑定必须关联 `app_id`、用户和数据源，具备轮换、撤销和清理路径。撤权、
用户解绑、Capability 停用和 Run 取消时，相关委托记录必须立即失效或撤销。

## 五、日志与审计

普通日志只记录稳定 ID、错误类别、计数和耗时；审计记录 Capability 调用事实，并由
集中清洗器处理。两者都不得记录凭据、认证头、Cookie、用户/模型正文、提示词、参数、
结果或原始上游响应。所有读取和写入在 API 与 SQL 边界按 `app_id` 隔离。

## 六、当前边界

校巴首期只读取公开、权威快照，不代表已获得校方真实数据授权。正式数据接入前必须
由用户确认负责人、授权方式、字段、频率、配额、保留删除和凭据轮换策略。
