# AI珞（爱珞）V3 鉴权与委托授权设计

> 状态：设计稿
>
> 本文固定 AI珞 的完整鉴权边界：身份认证（你是谁）、数据接入鉴权（机器对机器）、授权（你能做什么）三层分离；直接回答"服务器代持用户 access token 的隐私矛盾"；并把未来 Service/Tool 包管理器形态下的权限模型纳入同一契约。与 `v3_overall_design.md`、`校巴场景设计.md`、`数据需求与授权清单.md` 配套，不改动既有架构边界。
>
> **适用范围**：本文的鉴权边界只作用于涉及智慧珞珈数据/身份/委托 token 的部分；不涉智慧珞珈的包与能力保持独立，由 `docs/包管理器设计.md`（鉴权独立性）约束。

## 一、核心结论

1. **首期不存在"必须代持用户 access token"的矛盾**。校巴首期数据（站点、线路、班次、来源修订）是机构级数据，授权对象是 AI珞 Deployment（机构接入方），不是每个用户；用户隐私只出现在"要访问用户个人数据"的未来场景。
2. **用户 access token 属于委托凭证，不是身份凭证，更不是密码**。一旦未来需要用户个人数据，走 OAuth2 授权码 + PKCE 委托授权：用户密码永不到达服务器、最小 scope、短期 token、加密存储、可轮换可撤销。
3. **鉴权分三层，互不替代**：数据接入鉴权（机器 ↔ 智慧珞珈）、身份认证（用户 ↔ AI珞）、授权（每次调用实时计算）。
4. **包管理器形态下，安装 ≠ 授权**：安装包声明的 `requested_permissions` 只是权限上限的记录，App 显式启用并授予后才生效；升级不自动扩权。

## 二、用户的 access token 隐私矛盾

### 2.1 矛盾的真实形态

"我们服务器访问智慧珞珈必须要用户 access token"成立的前提是：智慧珞珈只提供**以用户身份为上下文的数据接口**。这与首期需求（机构级公开数据）和"数据先写入 Go 统一存储"的边界都存在张力：

| 关注点 | 矛盾 | 结论 |
|---|---|---|
| 隐私 | 服务器持有用户 token，泄露即代表用户 | 首期用机构接口绕开；未来用委托授权 + 密文存储 |
| 独立性 | 用户 token 生命周期（过期/登出/撤销）会拖垮我们的能力 | 数据落统一存储快照，运行时不依赖用户 token 在线 |
| 授权边界 | 拿用户 token 访问的接口，返回的是"该用户的数据视图" | 校方若只给用户视图接口，说明该数据不属于机构公开数据，须重新评估授权 |

### 2.2 解决原则（按优先级）

1. **能不用就不用**：机构数据走机构授权，不引入用户委托。
2. **必须用时用委托协议**：OAuth2 授权码 + PKCE；用户密码永不到达服务器，授权发生在用户本机浏览器。
3. **最小 scope**：只申请当前 Capability 需要的最小数据权限。
4. **短期 + 可撤销**：access token 短期；refresh token 加密存储、轮换、可撤销。
5. **密文存储**：token 由 Go L1 托管加密，主密钥来自批准秘密源，明文永不落盘。
6. **不进日志**：token、refresh token、授权码、state、nonce 全部进入净化字段，正文永不记录。
7. **数据最小化**：拉取结果落统一存储并按快照治理，不镜像用户全量数据。

## 三、三层边界总览

```text
智慧珞珈 数据平台
   │  第1层 数据接入鉴权（机器 ↔ 智慧珞珈）
   │    模式A：机构授权（Deployment 凭据，首期）
   │    模式B：用户委托授权（OAuth2+PKCE，仅个人数据 Capability）
   ▼
Go 统一存储（快照 + 有效期 + 权威标记）
   ▲
   │ 业务查询只读统一存储，不直连智慧珞珈
campus Service / Tool
   ▲
   │ 第3层 授权（每次调用实时交集校验）
Go Kernel / Dispatcher
   ▲
   │ 第2层 身份认证（用户 ↔ AI珞）
QQ（allowlist → 受限身份）  Web（智慧珞珈统一身份 SSO）
```

三个入口（QQ、Web/SSO、未来其他平台）都落回同一内部身份模型，之后走完全相同的授权与调用链路。

## 四、第1层：数据接入鉴权

### 4.1 模式 A：机构级数据授权（首期）

- **授权对象**：AI珞 Deployment 作为机构接入方，不是具体用户。
- **凭据形态**：校方签发服务账号 / API key / 请求签名 / 推送订阅，只读。
- **凭据管理**：Go L1 秘密管理，与 QQ Token 同规则（受限秘密文件、不回显、可轮换、可撤销）。
- **数据流**：ingestion 任务拉取或接收推送 → 校验 → 原子快照替换（现有实现）。失败保留上一完整修订。
- **用户隐私**：此层不接触任何用户 token；用户身份只用于第 3 层授权判断，不用于数据访问。

### 4.2 模式 B：用户委托授权（仅未来个人数据 Capability）

启用条件（全部满足才实现）：

1. 校方确认提供个人数据接口并书面授权；
2. 存在真实 Capability 需要用户个人数据（如乘车记录、提醒、个人位置）；
3. 无法用机构接口替代。

流程：

```text
用户 → 我们 Web（智慧珞珈 SSO 登录）
     → 触发个人数据 Capability
     → Go 构造 OAuth2 授权请求（PKCE + state + 最小 scope）
     → 用户在智慧珞珈授权页同意（密码只在智慧珞珈侧）
     → 授权码回我们服务器
     → Go 交换 access_token + refresh_token
     → 加密存储于 Go L1（按 app_id + user_id 隔离）
     → Capability 调用时经 Go 委托客户端使用 token
```

### 4.3 token 生命周期与隐私保护

| 阶段 | 要求 |
|---|---|
| 获取 | 授权码流；TLS 全链路；PKCE 防中间人；state 防 CSRF |
| 存储 | Go L1 加密 at rest；主密钥来自批准秘密源；按 app_id + user_id 隔离；明文不落盘 |
| 使用 | 仅经 Dispatcher 授权的 Capability/Service 可触发；每次使用记审计（不含正文） |
| 刷新 | refresh token 轮换，旋转后旧 token 立即失效 |
| 撤销 | 三条路径：用户主动撤销、token 过期、安全事件（调智慧珞珈 revoke + 本地删除密文） |
| 清理 | Capability 停用 / App 撤权 / 用户解绑 → 删除 token；数据按保留策略清理 |
| 日志 | token、refresh token、授权码、state、nonce 全部净化；console/JSON 负向测试覆盖 |

## 五、第2层：身份认证

### 5.1 身份模型（现有实现，保持不变）

- **User**：Deployment 级内部用户，`user_id` 权威；外部平台标识永不替代内部 `user_id`。
- **ExternalIdentity**：App 级外部身份绑定，唯一键 `(app_id, platform, platform_space_id, platform_user_id)` → `user_id`。
- **AppMembership**：`(app_id, user_id)` + 角色 + 权限授予。
- **生效权限**：查询时实时计算（直接授予 ∪ 角色授予），不缓存；禁用、解绑立即生效。
- **fail closed**：身份缺失、未绑定、禁用、无成员关系一律拒绝；不创建匿名用户。

### 5.2 QQ 入口（已实现）

- 准入：群/私聊 allowlist。
- 开通：`EnsureQQIdentity` 幂等创建内部用户（确定性 `qq-user-v1-<hash>`）、成员关系、外部身份绑定。
- 身份强度：弱身份，只能访问 App 策略内的公开/只读 Capability。
- 未绑定/未获准：fail closed，回公共错误"平台身份未绑定"。

### 5.3 Web 入口 + 智慧珞珈统一身份（新增适配器）

- 协议：校方提供 OAuth2/OIDC 或 CAS；优先 OIDC（id_token 携带校方稳定标识）。
- 服务端验证：issuer、audience（我们的 client_id）、nonce、过期时间、签名；**绝不信任客户端提交的 user_id/user_name/session_id**。
- 映射：校方稳定标识（学号/工号）→ `AuthenticatedWebIdentity{PlatformSpaceID: "luojia", PlatformUserID: 校方标识, PlatformSessionID: 会话标识}`。
- 开通：首次登录按 QQ 同款 Provisioner 模式幂等创建内部用户 + 成员关系 + 绑定；是否要求管理员批准由产品决策。
- fail closed：未注入 `WebAuthenticator` 时聊天入口返回 401；SSO 不可用时 Web 登录不可用（产品可用性问题，不是架构违例）。

### 5.4 多入口身份归一

- 同一内部用户可绑定多个外部身份（`qq` + `luojia`）。
- **绑定必须显式、带验证**（例如 QQ 用户在 Web 完成绑定，一次性验证码），禁止自动合并——自动合并即身份冒充漏洞。
- 未绑定前，同一真实人在 QQ 与 Web 是两个内部用户，数据互不可见（App 隔离）。

## 六、第3层：授权（含包管理器形态）

### 6.1 权限标识与授予层级

- 权限标识形如 `domain.resource.action`（现有 `id.Permission` 模式）。
- 授予按层级收窄，任何一层缺省即拒绝：

```text
包声明上限（requested_permissions / required_permissions）
   ⊆ App 权限范围（policy.PermissionScope，App 控制面授予）
      ⊆ 用户生效权限（EffectivePermissions：直接授予 ∪ 角色授予）
         ⊆ Run 接受时快照（capability_scope / permission_scope）
            = 每次调用实际可用的交集
```

### 6.2 包管理器形态下的授权规则

未来 Service/Tool 是安装包（`ServiceSpec` / `ToolSpec` / `CapabilitySpec`），安装、启用、调用三阶段分离：

| 阶段 | 行为 | 权限状态 |
|---|---|---|
| 安装 / 注册 | 元数据进 Registry，清单校验、锁版本 | 权限只被记录，**不被授予** |
| App 启用 | App 控制面显式加入 `EnabledCapabilities`，并把 `requested_permissions` 收窄后写入 `PermissionScope` | 收窄后授予，App 级 |
| 用户授权 | 角色/直接授予落到用户 | 用户级，⊆ App 授予 |
| 调用 | 每次按交集实时校验（`Registry.NarrowPermissions`） | Run 级，接受时快照 |

关键规则：

1. **安装 ≠ 授权**：Registry 里有 Capability 不等于任何 App 可用；未启用即拒绝。
2. **只收窄不放大**：App 授予 ⊆ 包声明；用户授予 ⊆ App 授予；内部调用不得提权。
3. **升级不扩权**：包升级新增 `requested_permissions` 不会自动进入既有 App 的 `PermissionScope`，必须由受信控制面显式确认（generation CAS）。
4. **敏感权限分级**：对外副作用（`external`）、写（`write`）、个人数据访问（`personal_data`）默认不自动授予任何用户，需要显式授予 + 审计。
5. **委托 token 与授权层绑定**：token 是"数据通道凭据"，授权层决定"哪个用户、哪个 Capability 可以走这条通道"。token 密文记录关联 `app_id + user_id`；Capability 触发 token 前，Dispatcher 先完成权限交集校验，再放行。

### 6.3 调用时鉴权路径（现有链路）

```text
Access（QQ/Web）→ 第2层身份解析 → Echo 创建
→ App 策略校验（enabled capabilities、permission scope）
→ Run 创建时接受上界（capability + permission 快照，只收窄不扩张）
→ Capability 激活/调用：NarrowPermissions 交集校验
→ Dispatcher 最终鉴权 → Service → Tool（再校验）→ 数据
```

## 七、隐私与数据保护清单（token 场景）

| 项 | 要求 |
|---|---|
| 传输 | TLS；授权码流；PKCE；state/nonce |
| 存储 | Go L1 加密 at rest；主密钥来自批准秘密源；按 app_id + user_id 隔离 |
| 日志 | token/refresh/code/state/nonce 进净化；console/JSON 负向测试 |
| 留存 | 最小化；Capability 停用、App 撤权、用户解绑即删除 |
| 撤销 | 用户主动、过期、安全事件三条路径 |
| 数据 | 拉取落库按快照治理（source_revision、有效期、权威标记），不镜像全量个人数据 |
| 审计 | token 使用带 app_id / echo_id / capability_id / user_id，不含正文 |

## 八、实施边界（推荐顺序）

1. **第1层只做模式 A**（机构数据授权）：与校方确认机构接口形态（拉取/推送/文件交换/只读副本）与凭据轮换流程。不实现 OAuth2 用户委托——首期无个人数据需求。
2. **第2层实现智慧珞珈 SSO `WebAuthenticator`**（OIDC 优先，CAS 兜底），与 QQ Provisioner 共用身份开通模式。
3. **第3层保持现有实现**，把"安装 ≠ 授权"、"升级不扩权"固化为规则与测试。
4. **模式 B（用户委托授权）只固定设计契约**，等真实个人数据 Capability 出现并获校方书面授权后再实现。

## 九、验收清单

- 未绑定 / 未启用 / 越权 / 无身份全部 fail closed（在现有测试模式上扩展）。
- SSO 验证：伪造 id_token、过期、错误 audience、nonce 重放 → 拒绝；服务端不信任客户端字段。
- token 存储：密文 at rest；无明文日志；撤销后立即失效；刷新轮换后旧 token 失效。
- 包权限：安装不自动授权；升级不自动扩权；App 撤权即时生效。
- 多入口：同一人 QQ + Web 未绑定是两个隔离用户；显式绑定后共享 App 内身份与权限。
- 数据接入：机构凭据不进日志、可轮换；ingestion 失败保留上一完整修订；过期返回受治理错误。
